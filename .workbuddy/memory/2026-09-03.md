## 图引擎专项调研 → 输出《图引擎调研.md》

**任务**：确认后端是否采用图引擎框架（LangGraph 等），若有则讲清图运转逻辑。

**交付**：`docs/图引擎调研.md`（8 章，含代码坐标速查表）

**结论（重要，后续勿重复调研）**：**没有采用任何图引擎框架**。`requirements.txt` 仅 9 个基础库（fastapi/uvicorn/sqlalchemy/aiosqlite/python-dotenv/pydantic/pytest/pytest-asyncio/httpx）。

### 三层"图"概念的辨析（易混淆，已澄清）
1. **工作流控制流 = FSM，不是图**：`(phase, spec_status)` → `ACTION_TABLE`/`NEXT_ACTION_TABLE` 查表。有返工回环，DAG 不适用。
2. **`prompts/nodes/` 的 "node" = 提示词模板文件，不是计算图节点**：7 个 txt 被 `CodexAgentGateway` 6 个方法硬编码一对一调用，无注册/无路由/无状态通道。这是最容易误判的地方。
3. **WorkItem 依赖 DAG = 唯一的真图**，但**只校验不调度**。

### 依赖图完整链路（含断层）
生产(Agent 输出 local_key 引用) → 校验(5 道闸门 + Kahn 环检测，`decomposition_service.py:259-274`) → 落库(`:670`/`:735`) → 投影(`query_service.py:367`) → 前端展示(`ApiWorkspace.tsx:867`) → **调度执行：不存在** ❌

**断层三证据**：
1. 全库 grep `WorkItemDependency`，只有定义/写入/UOW 守卫/读出投影，**无任何遍历调度代码**。
2. `WorkItem.status` 是死字段：`_work_item()` 构造时不传该字段（`decomposition_service.py:773`），永远为默认 `"todo"`。全 `app/` 无 WorkItem.status 写入点。
3. 前端 `workItemLane()` 泳道算法很完备（映射 15 种状态别名）但永远落在 todo 格；`workspace.test.tsx` 里的 in_progress/completed 是手写 fixture，非后端可产出值。

**性质**：不是 bug 是阶段边界。README 定位第一阶段 = 需求澄清/PRD 审核/任务拆解工作台，拆解是终点不是起点。佐证：`WorkItem.executable` 字段已埋好（`= kind is TASK`），是未来调度器的天然入口，当前无人消费。

### 图算法细节（值得学的工程手法）
- `_kahn_leftovers`（175-189）：只返回"没剥掉的节点"（环成员 ∪ 环下游），**不返回拓扑序**——因为没有调度器。全程 `deque` 迭代无递归。
- `_cycle_participant_iterative`（192-221）：DFS 三色标记 + **显式栈**（frames 存迭代器）防爆栈。关键：`return min(path[position[dependency]:])` 取环路径上**字典序最小** key，保证报错确定性，便于写断言测试。末尾 `raise RuntimeError` 是不可达断言。
- 边方向：`from → to` =「from 依赖 to」（指向前置）。注意代码里变量叫 `inbound` 但存的是出度，命名与方向相反，算法自洽但易读错。
- 依赖信息**三重冗余**（关系表 / AgentSpec JSON 列 / AgentSpec content 内嵌并参与 `content_hash`）——刻意设计，让 AgentSpec 成为自包含执行合同，下游 Agent 无需回查数据库。

### 若要补成真执行引擎的最小改动（已写入文档第 6 章）
补 status 生命周期 + 新增 START/COMPLETE/FAIL 命令注册进 ACTION_TABLE → 复用 `_kahn_leftovers` 的思路写就绪判定器（`deps <= done`）→ 用 `executable` 过滤 → 前端把分列依据从 `kind` 换成拓扑深度。**前提**：先解决 `_ACTIVE_PREPARATIONS` 是 process-local 的问题，否则无法并发执行多任务。

## 实施计划 → 输出《任务执行引擎实施计划.md》

**任务**：把依赖图改造成可执行调度引擎的可落地方案。

**交付**：`docs/任务执行引擎实施计划.md`（分 P0/P1/P2/P3 四期，可独立验收）

**调研中确认的关键机制（供实施时直接引用，勿重复查证）**：

### 现有机制给的免费能力
- `init_database` 末行是 `Base.metadata.create_all`（`database.py:41`）→ **新表只需在 models.py 定义，不必写 `_migrate_sqlite_*` 迁移**。
- 幂等（command_id + input_hash）、乐观锁（expected_state_version CAS）、租约恢复、审计留痕，新动作注册后自动获得。

### 三个拦路点（决定性）
1. **`_enforce_guard`（`:855-889`）会拒绝修改 WorkItem**：`allowed` 元组只管"新增"，`db.dirty` 豁免只给了 AgentCall（限 `status/completed_at`）和 ReviewTask（限 `new_spec_version_id/new_version`）。→ 因此**必须走 append-only 的 `work_item_runs` 新表**，不能直接改 `WorkItem.status`。这也契合系统整体 append-only 哲学（SpecVersion 不可变、AgentCall 追加）。
2. **`PrepareContext` 没有 db session**（`:74-81`，只有 project_id/session_id/request/input_hash/state）→ prepare 要查库须照抄 `ProjectService(session_factory, ...)` 模式自行持有 session_factory。
3. **`_targets`（`:898`）不注册就恒失败**：查不到返回空集，`not in set()` 恒真 → 报 "invalid workflow transition"，极具误导性。新动作必须显式注册自环。

### 其它确认
- `CommandService._handlers` 注册表**是真实生效的**（`:465` / `:548` 有消费），在 `sessions.py:39` 的 `build_router` 里注入。
- `ACTION_TABLE[(AGENT_SPECS_READY, APPROVED)]` 当前是 `()` —— 新执行动作加在这里。
- 前端已有 `Map<fingerprint, commandId>` 幂等，指纹含 payload，不同 work item 的动作天然不冲突，无需改。

### 三个实施坑
1. `QueryService._dependencies()` 只为**有依赖边**的 item 生成 key → 就绪判定必须 `dependencies.get(id, ())` 兜底，否则无依赖任务永不可就绪。
2. 前端 `workItemLane()` 不认识 `failed`，会静默归到 `todo` → 必须补。
3. P1/P2 的 prepare 不调 Agent（`agent_backed=False`），租约窗口极短，单进程 OK；**P3 要调 Agent 则必须先外置租约**（可复用数据库行锁 + `prepare_owner_started_at` 超时判定，照搬 `IntakeAnalysisClaim` 的 30s租约/5s心跳模式）。
