## 导入 PRD 大修：目录错乱 / 图片全丢 / 表格不可读（同日晚）

用户报告三件事，逐个定位到根因并修好，最后要求**把修法写成可重复执行的规则而非一次性补丁**。

### 根因一：层级只存在于字号（目录错乱的真正原因）

源 DOCX **完全没有 Word 大纲**：1892/1892 段样式都是 `Normal`、`outlineLvl=None`，
**没有任何一段带 Heading 样式**；680 段有 Word 自动编号，但**没有一段标题带自动编号**。
层级只活在字号里：26pt 文档标题 / 18pt L1（12 章）/ 16pt L2（54）/ 15pt L3（139）/ 14pt L4（24）/ 11pt 正文（1587）。

→ 旧提取器把这 1892 段压成一整块 299k 字符的扁平文本，Agent 只能"猜哪些短行是标题"，树自然错。

修复：`prd_source_import._docx_size_levels()` 用字号直方图推层级
（最频繁=正文；比正文大的降序编号，上限 6 级；**只出现一次的字号=文档标题要剔掉**）。
有真 Heading 样式时它优先，所以将来文件换成规范样式也不会退化。

### 根因二：只有标题、没有正文的章被整个丢掉

`split_imported_markdown()` 在"章标题紧跟子标题"时产不出 body part，旧代码 `continue` 掉整节
→ 该章消失、其下所有小节被重新挂到前一章下（树看着合理、父节点全错）。已改为保留空 body 的块。

## 「文档候选任务」失败根因：**模型是对的，执行器错了**（16:35，job `prdjob_e197ea55b9ae4d08b5e63563d350ea83`）

用户指令：把「用户问题」块第二张表的 P1 与 P5 条目互换位置（用 `chat_edit_plan`）。
任务跑满 151s、模型调用 `success:true`，最终 `failed`，`error = 表格行定位不唯一，请补充行名`。

### 定位链路

`prd_document_jobs`（列名是 `kind`/`payload`/`events`/`error`，**没有 `title`**，标题由
`DocumentJobs.view()` 从 `payload.instruction` 现算）→ `DocumentJobs.execute` →
`workbench.edits.plan()`（`document_edit_service.py:436`）→ `_simulate`（:351）→
`_table_edit`（:213）→ 抛错在 **:257**。

`_simulate` 是在 **deepcopy 上逐步顺序应用** `plan.steps`，每步重新解析被前一步改过的 content。

### 复现方式（重要：模型产物默认不留痕）

- `agent_calls` **不记录** `chat_edit_plan`（只有 analyze_brief / recommend_lifecycle / structure_imported_prd 等）。
- `ReviewCache.key()` 只对 `('review','document_quality_review','document_registry_review')` 生效，
  **`chat_edit_plan` 永远 key=None → 不入缓存**（且 ttl=900s、纯内存）。所以失败方案哪儿都没存。
- Codex 的 `%TEMP%/codex-structured-*` 工作目录跑完即清理。
→ **唯一取证手段是「同参数重放」**。可复现配方（在 `backend/` 下、用 `.venv/Scripts/python.exe`）：

```python
# 1) .env 必须在 import app.* 之前加载（database.py 在模块导入时建 engine）

# 2) 沙箱注入的 HTTP_PROXY/HTTPS_PROXY 会让 Codex 报 502，必须剥掉

```
之后再拿 `plan.steps` 喂 `document_edit_service._table_edit(content, step)` 逐帧复演即可。
被编辑块 `block_bf6de87d9e214e93ad421860084370f4`（title「用户问题」）内含**两张表**：
`table_index=0` 是 7 列 FR 覆盖矩阵，`table_index=1` 是 `编号/问题描述/证据 / 表现` 的 P1–P5 清单 —— 用户要改的是后者。

### 真相：方案本身完全正确、且每一步 `row_match` 都唯一

模型回了 **6 步 `table_set`**（把 P1/P5 两行的「编号/问题描述/证据」三个单元格逐一互写）：
step0-2 `row_match="P1"` 写 → row1；step3-5 `row_match="P5"` 写 → row5。
在**原始** content 上 `P1`→1 行、`P5`→1 行，都唯一。

**但 step0 把第 1 行的「编号」从 `P1` 改成 `P5`** —— 从此：
`"P1"` → **0 行（不存在了）**，`"P5"` → **2 行（第1、第5行）**。
→ step1 直接抛 `len(matched) != 1`。**把 step 顺序反过来也照样挂**（镜像同理），
即**这份方案在任何顺序下都不可能成功**。

### 两个代码缺陷

1. **`row_match` 在执行期被逐步解析，锚点会自我失效**（`document_edit_service.py:253-258`）。
   `row_match` 是内容锚；而"交换行"这个动作**必然搬运锚点字符串本身**，
   所以任何"逐单元格改写"的方案都注定自毁。DSL 里**没有行重排原语**
   （动作枚举只有 `table_set/table_add_row/table_delete_row/table_add_column/table_delete_column/table_sort`），
   模型只能用 6 步 cell 写去表达"换行"，于是踩中。
   反面证据：`document_candidate_reuse.py:69` 那条复用路径**恰恰已经把 `row_match` 折成具体 `row` 号**
   （`result.row_match = ''`）—— 说明代码库自己知道位置式才可靠，只有 `_simulate` 这条路没做。
2. **错误信息把两种状态混为一谈**（:257）：`len(matched) != 1` 对 **0 匹配**与 **≥2 匹配**
   都回"表格行定位不唯一，请补充行名"。本例是 **0 匹配**（行已不存在），
   提示"补充行名"是误导且不可行动 —— 越补越不可能成功。且报错**不带步骤序号、不带候选行**。

### 对照实验（证明错在执行器）

| 实验 | 结果 |
|------|------|
| (a) 原方案 | step1 FAILED |
| (b) 同方案、把 `row_match` 清空改走 `row`（位置式） | **6 步全过** |
| (c) 提出修法：首次见到该表时用**改动前快照**把 `row_match` 解析成行号，之后走位置式 | **6 步全过** |
| — | (b)(c) 产出的表都**精确等于**用户要的互换结果（P5 在第1行、P1 在第5行） |

`row` 字段模型**本来就填对了**（1 和 5，与 `row_match` 一致），只是代码优先用 `row_match`。

### 建议修法（未实施，待确认）

- **最小补丁**：在 `_simulate` 里给每个 `(block_id, table_index)` 记一份**首次接触时的行快照**，
  把 `row_match` 解析成具体 `row` 后再交给 `_table_edit`（快照行数与当前不一致时回落到实时匹配，
  以兼容 `table_add_row`/`table_delete_row` 这类结构性步骤）。
- **结构性补丁**：给动作枚举加 `table_move_row`（含 before/after/交换），让"交换/上移/下移"成为
  **单步原子操作**，从根上消灭自失效。
- **可诊断性**：拆开 :257 的两种状态。0 匹配 → "未找到匹配行「X」；现有行：…"；
  ≥2 → "行「X」匹配到 N 行，请给更完整的行名或直接给行号"。并带上步骤序号。
- **注意**：不要为了"让文件先好看"而手工改库；这条链路的重试也**大概率还会挂**（见下）。

### 一个反直觉但重要的结论

用户看到 `失败，可重试` 会以为重试就行。**本例重试基本一定再挂**：
"交换两行"在当前 DSL 下只能表达成搬运锚点字符串的 cell 写，而那种形状在任何顺序下都自毁。
所以这不是"偶发模型抽风"，而是**结构性缺陷**——必须先修执行器。

### 根因：`<img src>` 永远带不上 `Authorization`

资产端点是 `GET /prd-documents/{id}/assets/{asset_id}`，函数体内

```

带 token :  status=200  type=image/jpeg  bytes=54610   JPEG magic \xff\xd8\xff ✓
```

54610 与 `prd_document_assets.size_bytes` 逐字节一致，钉死「只差一个头」。

## PRD 插图二次破图：react-markdown 静默吃掉 `asset:` 协议（同日第三轮）

用户反馈「图片还是无法显示」，截图是**破图 + alt 文本 `image-21.png`**。

### 判别关键：截图上的破图说明「新组件根本没在渲染」

上一轮新增的 `DocumentAssetImage` 在两种态下渲染的都是**文本**
（`图片加载中…` / `图片未能加载：…`），不会产生破图图标。
截图里是原生破图 + alt → 说明 `img` 回调走的是 fallback 分支，`assetIdFromSrc()` 返回了 null。

### 决定性证据（一条命令）

```
node -e "const {defaultUrlTransform}=require('react-markdown');
  console.log(JSON.stringify(defaultUrlTransform('asset://asset_6ae…')))"
→ ""
```

`react-markdown@10.1.0` 的默认 URL 白名单只放行 `http/https/irc/ircs/mailto/xmpp`，
**其余协议静默清成空串**。所以 `src` 传到 `img` 组件时已经是 `''`
→ `assetIdFromSrc('')` → null → fallback 渲染 `<img src="">` → 破图 + alt。

**这是二次踩坑的机制**：上一轮我把「把 `asset://` 改写成后端 URL 的正则」删掉、
改成让组件自己去解析 `asset://`，恰好又落进了一个**新的清洗层**。
两次成因不同（401 vs 协议被清空）、症状完全一样。

### 修法

`DocumentAssetImage.tsx` 新增导出 `assetUrlTransform`：放行 `asset:`，其余交给 `defaultUrlTransform`
（保留对 `javascript:` 的拦截）。挂到全部两个 `<ReactMarkdown>`：
`RenderedPrdDocument.tsx:199`、`BlockEditor.tsx:18`。

### 验证

| 检查 | 结果 |
|------|------|
| 新测试 `DocumentAssetImage.test.tsx` | **4 passed** |
| 可逆基线探针（把放行改成直通） | **2 failed / 2 passed**（恰是依赖放行的两例变红） |
| `tsc --noEmit` | 通过 |
| 端到端取图（image-21.png，带 token） | **200 / image/png / 109390 B，PNG 魔数正确，与库 `size_bytes` 一致** |

### 教训（并入排障方法论）

**「破图 + alt」不能直接归因于 401。** 先看渲染出的到底是组件自己的加载态文本，还是原生破图：
有文本 = 请求层失败（A 类，token/权限）；原生破图 = `src` 根本没到组件（B 类，被清洗/被改写）。
另外：**凡是在 markdown 里用自定义协议，第一件事是确认渲染器有没有 URL 白名单。**

## 表格改行任务连败：两个叠加的 bug，都在执行侧（同日第四轮）

用户报告：「把『协同』整行放到最下面、名字改为『协作』」失败。
job `prdjob_100075164c5448398929d0936ae7c214`（rev 11，18:23 本地）。

### 取证：这次**不用重放模型**

错误信息 `未找到匹配「协同 | 消息中心、待办、评审组件框架（…） | FR-4.1–4.5、FR-8.1–8.7」的数据行；
现有行首列：…、协同、插件框架` —— **row_match 原文已经在里面了**，所以可以离线确定性复现（省掉 150s）：
把该字符串与表格各行比对 → 与第 7 行**完全相等**（`" | ".join(cells)` 形态），
而现有 `_row_hits` 对它返回 `[]`。

### Bug 1：行名锚点是「整行拼接」时必然 0 匹配

`_row_hits(row_match, row)` 的 `row` 是**单元格列表**：
`row_match in row` 要求整行文本**恰好等于某个单元格**；`any(row_match in cell …)` 要求它是某个
单元格的**子串** —— 整行 100+ 字，两条都不可能成立。而模型看到的表格就是整行，所以它经常按整行填。
**模型给的行名 100% 正确，是匹配器看不到它。**

修：`_row_hits` 四级匹配 —— 单元格 → 规范化整行拼接 → 多段逐段落格 → 退回首列
（新增 `_squash()` 去掉 markdown 填充空格）。退回首列若命中多行会走「匹配到 N 行」，
与 `step.row` 冲突会走「表格行号与行内容不一致」—— 都不会静默改错行。

### Bug 2：236 块的文档在收尾自检被 100 上限卡死

修好 Bug 1 后**重放模型**，立刻暴露第二层：

`_simulate` 收尾（464-470 行）用**全部块**构造 `BlockPlan` 做目录自检，而 `BlockPlan.blocks`
的 `max_length=100` 是**模型输出契约**（`plan_outline` / `ai_service` / `parse_outline` 在用）。
同一形状被复用到**本地自检** → 本机 236 块的文档**任何一次聊天修改都必然在收尾自检炸**。
17:04 与 17:20 那两条 job（指令是上一轮的 P1/P5 互换）也死在这里，只是报错被模型形状的不同掩盖了。

## 工具栏改造：「审核当前块」→「对比上一版」内联高亮（同日晚）

需求：删掉「审核当前块」，换成「对比上一版」勾选项；勾选后在**图文阅读**状态内联高亮与上一版的差异
（上一版原有的部分用红色删除线，本次新增用另一种明显方式）；不勾选则按当前状态显示。

### 关键约束：没有 rehype-raw，决定了整个实现形态

项目只有 `react-markdown` + `remark-gfm`，**没装 `rehype-raw`** —— markdown 里的内联 `<del>`/`<ins>`
**不会被解析成元素**。所以内联高亮只能借**原生 markdown 语法**表达，再由渲染层覆盖组件翻译：
- 旧内容 → `~~文本~~`（GFM 删除线）→ 覆盖 `del` 组件加红色删除线
- 新内容 → `[文本](#ff-ins)`（伪链接）→ 覆盖 `a` 组件，识别这个 href 翻译成 `<ins>`
  （纯 markdown 没有"插入"语法，只能借链接当载体）

### 表格为什么必须做到片段/单元格级

行级 diff 之后若**整行**包 `~~`，会得到 `~~| 协同 | 消息中心 |~~`。实测 remark-gfm 对**含 `|` 的行
依旧按表格行处理** —— 表格**不会断**，但整行文字被**挤进第一个单元格**、第二格空着，管道符还当正文显示。
→ 分两步：成对的删/改行做 **token 级行内** diff（中文逐字切分，`协同`→`协作` 只标出 `同`/`作`，
而不是整词删加）；整行增删且该行是表格行时**逐单元格**包裹。

### 「上一版」怎么定位（数据实测）

该文档 `prd_document_versions` 有 v1–v11，而当前 revision = 12。实测 **v11 与当前内容逐字相同**
（每次改动同时推进 revision 并写快照），**v10 才是上一版**（与当前只差「协同→协作」那个块）。
→ 不能取 `max(version)`，必须**从最新往回找第一个内容与当前不同的快照**（`api.findPreviousVersion`）。
