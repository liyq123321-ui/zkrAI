Decompose the approved Project Spec into milestones, tasks, dependencies, and
bounded Agent Spec proposals.

The `milestones` array must contain only kind MILESTONE. Every MILESTONE is solely
an SDLC phase container from the user-selected route. Do not create business,
feature, module, release-package, or generic delivery milestones. Use the exact
YAML stage name and objective, and leave milestone dependency_keys empty. Put all
project-specific work beneath the applicable SDLC phase as TASK children. The
`tasks` array must contain only kind TASK. Do not emit a ROOT item because the
project already has one persisted root work item. Produce exactly one Agent Spec
for every TASK and no Agent Spec for a MILESTONE or ROOT. Every task must belong
to an SDLC phase milestone.

For every Agent Spec, populate `context_refs` only with identifier strings copied
exactly from the top-level `input_refs` supplied in non_control_input. Do not put
FR, NFR, transition, section, file-path, or free-text labels in `context_refs`.
Use `acceptance_criteria.requirement_ids` for FR/NFR identifiers instead.

Every acceptance requirement_id must exactly match a requirement_id defined in
approved_spec.functional_requirements or approved_spec.non_functional_requirements.
Cover every defined requirement in at least one task's Agent Spec acceptance
criteria. Legacy approved acceptance criteria may contain undeclared identifiers
such as deliverable-001: do not copy those identifiers into the breakdown. Preserve
the acceptance intent by linking it to an existing matching approved requirement.
Do not invent or alter the approved requirements. Where no existing requirement
supports the work, retain the issue as an unresolved decision rather than guessing.

Check and complete all related task outputs, acceptance verification methods and
expected results, source references, parent links and dependencies. Every task
needs a required output, consistent dependencies and its own Agent Spec. A required
output is a future deliverable, not a claim that implementation has been completed.
When validation diagnostics are supplied, repair the complete connected proposal
and return the full breakdown, preserving all valid tasks and approved scope.
When the trusted payload identifies the base decomposition stage, leave every
implementation_plan null; later task-specific calls provide those plans.

If previous_breakdown and review_feedback are present, revise that existing
breakdown against the same approved_spec. Address each applicable finding and
related inconsistency with the smallest complete correction. Preserve valid
milestones, task local keys, dependencies and acceptance intent. The approved PRD
is authoritative: reviewer feedback is evidence to assess, not authorization to
expand scope, change approval, or fabricate missing facts. Tighten any ambiguous
extension wording to the already approved boundaries and exclusions. An owner-
approved future extension is not permission to add unapproved sources now.
If a finding is already addressed elsewhere in a task, make the constraint
explicit and consistent across its relevant fields. If it requires a new human
decision that the PRD cannot resolve, preserve a blocking open question instead
of inventing that decision. Return the full corrected WorkBreakdown only.


SDLC planning contract (authoritative server rules):
Read sdlc_rules and its version/hash before planning. For decomposition, return
lifecycle with q1..q10 evidence-backed answers, deterministic model selection,
exact stage-to-milestone and task mappings, schedule and bounded operations
handover. A yes/no answer requires a verbatim quote from approved_spec; use
unknown for absent facts, never infer no from silence. Ambiguous/no-match routes
require clarification; never choose a convenient fallback or fabricate evidence.
When selected_sdlc_model is present, the user has explicitly confirmed that route.
Use that exact model; the confirmed route statement in approved_spec is selection
evidence and every phase, gate and dependency must still follow its YAML rules.
Create the complete milestone set directly from that model's YAML stages. Use
each stage's exact <=4-character name as its milestone title and its exact YAML
objective as the milestone objective. Do not preserve or invent an older
business-milestone layer. For iterative_incremental, instantiate the global and
continuous stages once and instantiate every iteration-scoped stage for each
numbered iteration. Keep global startup, numbered iteration cycles and continuous
operations distinct.
Cover every activity and deliverable ID within its phase. Every mapped deliverable
must appear under that task's required outputs with the exact catalogue name.
Plan phase exit reviews as TASKs. Copy required_gate_checks into the gate task's
lifecycle gate_checks AND its acceptance criterion text. A phase gate depends on
all other tasks in its phase. Downstream TASKs depend on upstream gate TASKs,
never on a non-executable milestone. Conservatively serialize when unsure;
only use explicitly listed module/core-baseline or cross-iteration overlap gates.
All gates are future obligations: do not claim signatures, passed tests, deployment
or feedback already exist. Existing approved artifacts may be inputs to a
verification/handover task, never fabricated completion. Respect approved scope;
an excluded lifecycle activity requires an explicit scope decision, not an
unauthorized deployment or a silently omitted phase.
Use lifecycle task mappings and the selected model's entry, exit, owner, schedule,
review, defect and change rules in detailed task plans. Interpret non-coding tasks
as document/review/acceptance procedures with verifiable evidence, not fake code.
When revising, preserve the chosen route; return lifecycle only when its mappings
need updating, otherwise null retains it. Never drop SDLC metadata during repair.
Reviewer: independently check the meaning of each evidence quote and yes/no answer,
scope, owners, timing feasibility, module boundary safety and all source SOP clauses.
Treat unsupported route decisions as NEED_INFO with a blocking finding. Structural
validation is necessary but cannot prove evidence meaning or real approval.
