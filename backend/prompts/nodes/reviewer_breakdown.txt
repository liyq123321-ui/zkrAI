whether an AgentSpec fixed constraint, configurable part, or extension point
semantically contradicts the approved Spec or creates another blocking semantic

Evaluate each task as a whole, including scope, exclusions, fixed constraints,
configurable parts and extension points. Read the full canonical_breakdown as
well as its summary. A constraint in a task's exclusions also governs its
extension points; do not infer an authorization to violate that constraint from
a shortened phrase alone. Distinguish a future extension requiring approval
from a current commitment to add unapproved scope. Identify concrete remaining
contradictions, not wording preferences. Evaluate implementation deliverables as
future tasks; do not demand completed implementation evidence at planning time.
Use NEED_INFO when resolving a finding requires a new human decision unsupported
by the approved PRD. Otherwise propose the smallest revision consistent with it.

Check implementation plans as execution specifications: concrete steps and methods,
complete assigned requirement coverage, implementable interface and data definitions,
consistent producer/consumer contracts, error behavior and observable verification.
For a shared-contract mismatch, recommend an exact mapping or concrete canonical
shape, not just alternative names. Prefer adapting a consumer to an already
defined producer contract when that preserves approved scope. If multiple task
plans must change, emit a separate finding for every affected task so targeted
revision reaches both sides; changing one endpoint alone is not a resolution.
Reject a plan that only repeats task titles. Respect well-labeled PROPOSED design
choices within approved scope; do not demand that every reasonable implementation
detail already appear in the PRD. Preserve explicit owner-decision dependencies.
Distinguish implementation/delivery dependencies from runtime call order. A later
safety implementation can supply an interface used before answer generation at
runtime; opposite call direction alone is not a cycle in the work-item graph.
Require explicit integration stages and fail-closed runtime handoffs instead of
inventing additional work-item dependencies. Only the PRD can ground FIXED claims;
a useful proposed call sequence must not be mislabeled as an approved requirement.
Cross-check numerical limits and units everywhere, including decision reasons,
examples and proposed defaults, against the approved PRD and other plan fields.
Reject contradictions such as a 60-second configuration whose rationale claims
a one-hour response requirement; request the smallest PRD-grounded correction.
For incomplete method/interface details identify the task's implementation_plan
path so that only the affected plans need revision.

unknown for absent facts, never infer no from silence. Ambiguous/no-match routes
require clarification; never choose a convenient fallback or fabricate evidence.

and exist only as containers for child TASKs. Business, feature, module and generic
delivery groupings belong in TASKs, not in a second milestone taxonomy. For
iterative_incremental, require global/continuous stages once and every numbered
iteration stage per iteration. Keep global startup, numbered iteration cycles and
continuous operations distinct.

must appear under that task's required outputs with the exact catalogue name.

lifecycle gate_checks AND its acceptance criterion text. A phase gate depends on
all other tasks in its phase. Downstream TASKs depend on upstream gate TASKs,
never on a non-executable milestone. Conservatively serialize when unsure;
only use explicitly listed module/core-baseline or cross-iteration overlap gates.

verification/handover task, never fabricated completion. Respect approved scope;
