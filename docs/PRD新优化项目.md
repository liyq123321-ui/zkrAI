# PRD新优化项目

更新日期：2026 年 10 月 7 日（补充任务检索、候选快捷复用与决定草稿恢复）

PRD 编辑页面已经具备一条连续的工作路径：输入需求生成初稿，在 Agent 对话框中修改正文、表格、目录和配图，通过批注与全文审核完善需求，再用版本对比检查改动，最后基于确认的版本生成原型和演示材料。

本文汇总当前代码中已实现的功能，给出可直接尝试的操作示例，并整理下一步值得考虑的优化。已实现表示相关页面和处理逻辑已经接入；图片服务、Office 工具和模型调用等能力仍受本机配置影响。后半部分保留完整候选方向，本批落地项已标注状态，尚未完成的方向没有正式排期。

### 本批可直接试用

1. 在影响地图选择需要同步的章节，填写规则，点击生成联动候选；从候选任务逐组预览。
2. 收集待确认信息，忽略不需要的问题；保存答案后生成候选，应用后查看写入版本。
3. 在对话输入“确认业务决定：本期游客只读”或“保存本文档编辑偏好：对外说明少用缩写”。也可在决定面板设置章节、理由及需求编号。
4. 手动执行审核后查看“耗时”面板；重复完全相同的符合条件的只读审核，核对是否标明缓存命中。点击下一阶段仍重新执行所需审核。

本批采用 5 项后端定向检查，覆盖候选分组范围与重复请求、答案实际写入回执、一次偏好与决定撤销保护、跨章验收、缓存命中与门禁绕过缓存。模型调用使用替身；实际使用速度和模型判断质量由后续试用确认。前端更新需刷新，后端代码需服务重启后生效。

### 本批建议试用

1. 选中一段已保存正文，在输入区填写“不修改金额”，固定对象；刷新后检查卡片，再发“继续精简这里”。
2. 点击“选择表格单元格 / 图中对象”，选择“编号”列作为业务定位列，点目标优先级单元格，再发“改成 P1”。
3. 打开修改预览，分别勾选独立段落/单元格，确认下方只显示所选改动。
4. 候选生成后手动调整别处内容或表格排序，再打开原候选，点“核对最新正文并复用所选候选”；检查冲突后打开可复用部分的独立预览并应用。
5. 对同一单元格制造人工改动，确认默认保留人工值；只有勾选“此单元格采用候选值”并重新核对后，新的预览才采用候选值。

本批无数据库结构变更；重启后端加载新接口，前端开发模式刷新，静态部署需重新构建。本批未代为重启或部署。正文依然显式保存，修改后默认不自动审核。

3. 生成失败时只重试失败任务；更改过 PRD 后选择“基于当前版本重试这一项”。
4. 在方案要求或正文中输入尚未保存的内容，刷新后选择恢复，确认内容只回到输入区。
5. 输入“比较 v3 和 v5，生成评审会议包”（替换为实际版本号），从操作结果下载；随后可从这条对话重新打开保存结果。

本批仍复用原有文档修改 Skill 路由，不为明确的查询/收集/版本操作额外增加模型调用。新后台任务只生成候选，正文必须经预览后明确应用；默认不在每次改动后审核。

需要重启后端以注册新任务表和接口；前端开发模式刷新，静态部署重新构建。尚未替用户重启服务或发布。定向检查记录为后端 4 项、草稿恢复 2 项及 TypeScript 检查，未执行全量测试。

## 已实现的阅读与评审体验

### 文档空间更集中

右侧原来的大面板收为图标 Dock，按需展开生成消息、全部批注、全文审核意见和修订版本。正文获得更多横向空间，同时能看到批注数量、审核问题数量和任务提示。

文档支持图文阅读与源码编辑。目录用于定位章节，紧凑的结构图可展开查看。人工输入保留为本地草稿，由用户显式保存；离开时对未保存内容提供处理提示。同步机制会避免用无变化的快照反复重建正文，减少阅读选区和配图展示受到干扰。

### 批注能直接关联到文章位置

- 选中文字添加批注，正文显示高亮和批注入口，点击后查看对应内容。
- 在 Dock 中查看全部批注，包括尚未解决的批注。
- 可围绕当前章节、选定范围、多个章节或全文添加意见。
- 支持按批注发起修订，并将批注标记为解决或重新打开。
- 批注关联旧版本时进行检查，避免把旧位置直接当作当前内容的位置。

### 审核与修复形成闭环

全文审核检查跨章节一致性、范围、遗漏和验收等问题，保留问题级别、涉及章节和改进建议。审核本身不改正文；文档更新后，旧审核意见会显示其版本状态。

“自动解决审核问题”会根据现有问题生成修订。流程保留按影响范围压缩上下文、独立章节组并行修订和修订结果合并，默认在一轮修订后结束，等待手动复审。原审核意见继续保留并标记过期，需要业务决策的问题可以留给用户处理。

这里已经实现的是减少重复工作和支持有边界的并行。实际总耗时仍取决于模型响应、文档长度、问题数量和章节关联程度，尚不能承诺固定提速比例。

- **DOCX 导出与回传**：将正文、表格和图片导出为 Word 文件；带文档标识的文件回传时可更新对应章节，并检查版本冲突。

### UX01：一句话完成工作台操作

- **例子**：“比较 v53 和 v58，整理评审会议包。”“把这条批注加入资料缺失篮。”“第三个问题的答案是只支持管理员导出，先给我修改预览。”
- **首版范围**：把指令解析成可见操作卡，展示对象、版本、范围和即将执行的动作；直接复用对应接口。参数明确的读取、收集和生成预览无需再次填写表单，缺少关键对象时才询问。
- **应用方式**：会议包和查询直接返回结果；对正文的写入沿用预览与明确应用。当前 PRD 只提供默认上下文，明确指定其他对象时仍尊重用户目标。
- **完成判据**：用户能只靠对话完成“收集问题 → 回答 → 预览改动”及“指定两版 → 生成会议包”，操作结果和定位链接均进入对话记录。

### UX02：任务续接与失败恢复

- **例子**：生成 A/B 时先关闭工作台继续看 PRD，稍后在对话卡片中打开结果；B 超时只重试 B。
- **首版范围**：把工作台生成任务与普通待应用方案持久化，记录排队、执行、已完成、失败、取消和待应用状态；页面重连后获取真实任务状态，不靠原请求是否仍连接判断成功。
- **效率要求**：使用相同请求标识避免重复提交；应用也要防止重复写入。已完成结果保持可读，重试前校验源版本，旧结果保留供比较。模型服务若不能真正中止，界面明确区分“请求取消”和“已停止”。
- **完成判据**：离开/刷新不会丢失已接受任务和候选；两路中一路失败不拖累另一份已保存结果；取消后不会偷偷应用正文。

### UX03：可见、可移除的上下文卡

- **例子**：“继续精简刚才那段，仍然不要改数值。”隔一段时间重新打开后，能恢复明确的讨论对象。
- **首版范围**：保存最近明确引用的章节、原文位置、表格/图、方案、版本以及当前约束；对话输入框上方显示简短卡片，允许固定、换目标和移除。限制携带内容大小，不把全部历史反复送给模型。
- **失效处理**：正文变化后先校验对象身份和来源版本；无法唯一匹配时提示重选，展示候选位置。切换项目时不沿用上个项目的对象；未保存草稿只作为明确标注的参考，不能冒充已保存正文。
- **完成判据**：用户能看懂 Agent 本轮引用了什么；刷新后可恢复有效目标；失效的“这里”不会改到别处。

### UX04：可恢复草稿，继续由用户显式保存正文

- **例子**：信息篮中写了一半的答案、方案 A 的长要求，误关后重新打开仍能找回。
- **首版范围**：为正文草稿、待确认答案、方案要求、问题处理依据和未发送指令保存本机恢复副本，按账号、项目、文档及来源版本隔离；提供恢复、丢弃和清理入口。
- **保存语义**：恢复副本不发布为 PRD，也不生成全文版本。刷新后提示“发现未保存草稿”；与服务端新内容冲突时提供比较，不自动覆盖。
- **完成判据**：可恢复输入且不增加正文版本；退出账号后另一个账号看不到上个账号的草稿；存储失败有清晰提示。

### UX05：表格与图形的对象级修改

- **例子**：点“导出功能”这一行的优先级单元格，说“改成 P1”；点 ER 图“订单”的支付状态字段，说“补充退款中状态”。
- **首版范围**：先做 Markdown 表格的行/列/单元格选择和业务主键映射，再扩展支持的 ER 实体/字段及 Mermaid 节点。对话目标卡显示对象名称和所在图表，预览同时展示图表变化与文字说明。
- **定位规则**：业务主键缺失或重复时让用户选定位列，不猜测哪一行；图形源无法可靠映射时回到图源预览。节点改名要保留稳定身份，不能只靠展示名称。
- **完成判据**：表格排序后显示“行移动 + 单元格修改”，不会把整表误报成删除重建；对象修改不影响相邻行、实体或节点。

### UX06：更细的修改采纳与冲突处理

- **例子**：“这一段采用新版，表格保留我刚改的数值，其他两处照你的建议。”
- **首版范围**：把可独立应用的段落、单元格和图源改动拆成可选项，保留强依赖操作的共同选择；展示基线、当前正文、候选三方差异。未冲突项继续可用，冲突项明确选择保留人工版本、采用候选或重新生成。
- **恢复方式**：优先补上从历史版本取回一个段落/表格的预览；图文冲突按对象身份核对，不用模糊匹配强制覆盖。采纳前再校验版本，一次明确应用对应一个全文版本。
- **完成判据**：其他章节的人工修改不会导致整份候选必须重做；能证明未选中和选择保留的内容未被覆盖；目录移动等强依赖修改不会被拆坏。

### UX07：影响地图变成联动修改入口

- **例子**：“游客改为只读，请同步勾选的权限表和流程图，先别动对外 PPT。”
- **首版范围**：在已有影响节点旁增加选择框，展示关联证据与建议动作；用户核对影响范围后形成一份联动候选。超过一次处理容量时拆成可追踪的候选组，明确已完成、未开始和失败部分。
- **应用方式**：正文、表格、图源先统一预览；原型/PPT 继续遵守冻结版本要求，列出待更新清单和来源，不能把旧产物直接标成已同步。
- **完成判据**：用户不用逐个重新输入章节名称；漏选或暂不更新的关联项在回执里可见；不会因共同引用一个编号就无条件重写全部相关章节。

### UX08：减少误报、重复项和处理尾巴

- **例子**：把一句普通问句标为“无需确认”后不再重复出现；填写并应用一个答案后，能从已处理列表找到写入版本。
- **首版范围**：信息篮增加待答、已答待应用、已写入、忽略、归档及重新打开；相似问题只提出合并建议。健康地图跨章节核对验收覆盖，区分当前缺陷、资料未同步和旧审核待复查；支持只看当前需要处理的项。
- **状态证据**：只有成功应用回执才能标为“已写入”，保留来源问题、采用答案与目标版本；确认问题解决要保留依据，旧证据失效时按相关变化重新核对。
- **完成判据**：忽略项再次收集不会反复冒出；答案仅保存、候选生成失败或未应用时都不会显示“已写入”；别章已有有效验收时不再误报缺失。

### UX09：业务决定卡与明确的编辑偏好

- **例子**：“游客只读是本期已确认决定，之后不要再建议游客新增数据。”“对外介绍尽量少用技术缩写。”
- **首版范围**：从用户确认的答案或处理依据创建决定卡，包含结论、理由、来源、适用章节/需求、确认人及有效状态；编辑偏好单独保存，允许只用于本次、当前文档或项目。
- **调用方式**：生成、审核和图文更新仅携带相关有效决定；新指令与决定冲突时明确展示冲突，由用户更新或保留原决定。偏好不能覆盖已确认的事实、数字或用户本轮的明确要求。
- **完成判据**：同一决定在相关修改和复审中保持一致；用户能查看、撤销和替换它；过期或撤销的决定不会继续约束 Agent。

### UX10：基于证据的耗时优化

- **例子**：第一次复审 A 章后只改 B 章，再次手动复审不无差别重做 A 章的相同质量检查。
- **首版范围**：拆分排队、上下文准备、各 Skill 调用、校验和保存耗时；记录每类调用的范围与失败重试原因。按正文哈希、规则、关联内容、模型/Skill 版本建立复用条件，优先复用确定性索引与仍有效的局部结果。
- **并行边界**：独立候选或检查可在有上限的队列中并行；同一正文范围的写入串行校验。取消、容量不足或冲突时可降级，已确认的问题不为提高吞吐被跳过。
- **完成判据**：用相同规模样本比较总耗时、重复调用数、成功率和撤销原因；只有实测改善才称为提速。局部缓存不冒充当前完整审核，下一阶段仍要求完整有效证据；默认仍不在每次编辑后审核。

### 建议先选择哪些

**UX01–UX10 已实现首批范围**。先实际体验对话操作、后台任务、恢复、对象选择、联动及决定卡，再依据使用反馈补齐边界。

下一轮建议按 **UX11 → UX12 → UX13 → UX14** 选择，详见文末研究。这是产品候选顺序，尚未给出工程工期或正式阶段依赖。

后续实现仍采用快速交付方式：围绕所选范围做必要检查，主要体验验收由用户实际试用；版本保护、显式保存和已确认业务边界持续保留。

## 扩展研究：下一轮高收益候选（尚未实现）

- Tiptap 提供逐条接受/拒绝、暂存建议及持久修订记录，并支持把采纳决定反馈给 Agent。这提示我们优先把已有候选放到原文附近，让用户少跳转。[官方 Review Changes 文档](https://tiptap.dev/docs/ai/ai-toolkit/client/agents/review-changes)

- Linear 在项目概览中把项目说明、文档、资源与里程碑放在共同入口。结合本项目 PRD→Spec 的流程，可以用一个交接概览汇总已确认内容和仍有变动的来源。[官方 Project overview 文档](https://linear.app/docs/project-overview)

## 暂不列入最先一批的好点子

这些方向有价值，待高频编辑与恢复体验完善后再选：

- **反例助手**：为某条需求列出三种失败场景，用户认可后加入信息篮或验收候选，避免直接扩大产品范围。
- **规则试算器**：对额度、费用或审批阈值输入样例，展示公式来源和预期结果；规则不明确时先记录问题。
- **按读者切换阅读视图**：产品、研发、测试和对外阅读重点不同，始终可回到原文；对外公开范围由用户确认。
- **配图风格与服务配置**：保留 N17/N18；明确可用图片服务、默认风格和失败回退，后续图形沿用当前文档风格。
- **原型与 PRD 元素互相定位**：保留 N19；从页面元素回到需求，原型调整形成 PRD 候选，再更新衍生产物。
