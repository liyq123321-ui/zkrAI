# Block PRD 编辑器

本次是在现有 React + FastAPI + SQLite 项目中直接增加功能；按用户明确指示，不对这次代码修改另行套用 SDLC 项目规划。验收采用一次整体验收。

## 使用

1. 从项目对话区点击「编写 PRD」，或从 PRD 审核页点击「编写 PRD · Block 编辑」。独立页面地址为 `/prd-editor/<session_id>`，支持刷新恢复和返回项目。选定项目生命周期路线后的入口也直接打开编辑器，不再先等待整篇正文生成。
2. 首次进入尚未生成过正文的新文档时，立即显示阿里模板目录，并由后端按目录和依赖顺序连续生成所有模块，每块完成后保存再继续下一块。页顶显示进度，可「停止自动生成」。刷新、重复打开或多个页面不会重复启动；离开页面仍继续。已有正文、人工编辑历史、单块生成记录或已有 PRD 版本的文档不自动启动；后续修订仍按块手动操作。失败、取消、版本冲突或服务重启会停止队列，保留已有内容，剩余模块可手动继续，不因刷新自动重跑。
   若要改用其他大纲，先停止自动生成；在尚无正文和编辑历史时，可点击「AI 规划大纲」只生成结构，或通过「导入大纲」切换鹅厂模板、粘贴 Markdown/纯文本目录、上传文件。PDF/TXT/Markdown 文件先展示提取文字供确认，再导入并规划。PDF 限 8 MB、50 页，扫描件或加密文件明确报错。
3. 正文始终以一篇连续的 Univer/DOCX 画布展示，不再在“单块编辑”和“全文浏览”之间切换。左侧目录仍按 Block 导航；当前目录项和画布中的对应正文使用绿色虚线标识。当前 Block 的生成、编辑、审核、历史、依赖和图片工具保留在全文画布上方。文字输入约 900 毫秒后按所属 Block 保存；切换目录保留各自未保存输入。
4. 批注默认属于当前 Block；选中文字或填写起止行可定位该 Block 内的范围，勾选左侧目录可对多个 Block 添加同一条批注。只有主动勾选「全文批注」时才把全部 Block 作为目标，同时起始行和结束行变为不可用。「按此批注修改各块」仍为每个目标创建独立作业，旧版本行批注不会静默套用到新文本。
5. 手动触发的 AI 结果先保存为候选。页面只在无未保存输入、基线仍匹配时自动应用。首版连续生成由后端检查块版本、依赖和背景版本后应用结果；发生冲突即停止。两种模式均保留页面尚未保存的人工输入，提示与服务端版本比较后保存。候选可查看 Diff、基于当前版本重新生成、仍然应用。明确应用也检查当前版本，不能无条件覆盖。刷新时可重新看到未处理候选。
6. 「历史版本」可比较并恢复旧正文；恢复创建新版本，不回退计数。修改上游会传递标记下游已有正文为「待更新」，不自动重写。依赖在当前块的「上游依赖」中维护；规划图显示层级和当前块的上游关系。
7. 「审核当前块」仅提取该块的结构化规格并返回意见，不改正文。人工修改后提取结果失效。提交评审前，每个有正文的块和叶子块须完成内容与结构同步；没有正文的目录容器不需要生成占位文本。
8. 「提交评审」确定性汇总 Block 正文和结构片段，校验完整性、需求 ID、验收引用及其他既有规格规则，创建 `HUMAN_REVIEW` 状态的 `SpecVersion`。不自动批准、拆分或发布。错误提示会指出待补内容；不会偷偷回退到旧规格或调用 AI 重写整篇。
9. 编辑区不再显示「本块写作要求」输入框。右侧生成队列独立滚动，显示全部运行中和已结束消息；运行中排在前面，已结束消息按新到旧展示。成功、失败和取消消息支持单条删除，仅移除提示，不删除作业、正文、候选或版本记录。删除状态按文档保存在当前浏览器，刷新后保留；运行中作业只能取消，不能删除消息。
10. 全文画布顶部可直接「审核全文」，检查跨模块一致性、遗漏、范围和验收标准，保存摘要、问题级别、相关模块及改进建议。它不改写正文、修改块版本或结构片段，不自动批准或提交。意见在刷新后保留；审核期间或结束后正文/背景变化，会标明旧版本意见。全文请求超过 30 万字符时明确拒绝，不静默截断。失败可重试，运行中的审核可在队列取消。
11. Block 生成和修订结果在结构化合同校验后按完整句子/Markdown 行写入运行快照。SSE 将这些临时内容增量替换到全文画布对应 Block，显示为连续写入；最终正文仍必须通过原有 Block ID、基线版本、行范围和并发冲突检查后才正式应用。全文自动修订同样按 Block 分段流出。
12. 全文审核意见右上角的「自动解决审核问题」会创建 `document_revision` 后台作业。后端按审核意见修订相关 Block，再对最新全文重新审核；若仍有可自动处理的问题，最多连续执行三轮“修订 → 复审”。每次正文修改仍创建正常 Block 版本并检查并发冲突，最终页面展示最后一次复审结果。需要产品负责人决策的问题允许保留，不会无限循环或伪造“全部解决”。
13. 右上角「进入下一阶段」仅在当前版本全文审核没有 blocker/warning 时启用。点击后创建 `HUMAN_REVIEW` 规格快照；未过期的零待处理项全文审核可覆盖逐块结构抽取产生的重复需求 ID、验收映射等机械性门禁，具体发现仍写入审计事件。该动作不等于人工批准，也不会直接启动任务拆分。
14. 「导出 DOCX」先保存所有本地草稿，再由后端生成当前文档版本的共享编辑文件。DOCX 中的标题、正文、列表、表格、上传图片和现有 draw.io ER 图按 Block 顺序排版。每个章节包含不可见的文档、Block 和版本标识；用户在 Word 中修改后，通过「导入」回传同一文件，系统会把内容更新到原 Block 并生成正常的 `BlockVersion`，版本已变化时拒绝覆盖。
15. 「插入图片」把 PNG、JPEG、WebP 或安全 SVG 关联到当前 Block。文件存入后端文件系统，SQLite 只保存路径、尺寸、类型和来源等元数据；导出 DOCX 时图片自动进入所属章节。DOCX 中新增的图片在回传时也会提取成文档资产。已有 draw.io 源数据继续保留，导出时生成图像，后续仍可编辑源图并重新导出。

## 现有数据与运行方式

- 启动时在已有数据库中新增 `prd_documents`、`prd_blocks`、`prd_block_versions`、`prd_block_comments`、`prd_agent_runs`、`prd_document_assets`、`prd_document_artifacts`，不重建已有表、不改旧 PRD。DOCX 和图片二进制默认存放在 `backend/data/prd_assets`，可通过 `PRD_ASSET_ROOT` 修改；数据库只保存元数据、内容哈希和相对存储键。
- 每个 Session 一份持续编辑的草稿。首次打开已有 PRD 时按标题层级导入正文；标准规格章节同时保留对应结构字段和图引用。已存在正文、历史编辑或批注时，替换大纲会被阻止，以保护内容。
- 旧版本和 Gitea 审核记录继续保留；新 Block 快照通过既有 PRD 读取/绑定入口进入评审。旧 Gitea 评论与新 Block 批注分别保存。Block 快照的编辑按钮回到 Block 编辑器。
- `CodexProvider` 复用现有 `CodexStructuredRunner`。块编辑仅提供当前块、当前反馈、文档背景/规则及必要的上游摘要；仅在用户主动点击「审核全文」时，专用 `review_document` 合同提供全部模块正文，返回只读整体审核报告。两种操作均不提供聊天历史。使用现有 Codex CLI 配置和登录状态。可通过 `create_app(block_provider=...)` 注入其他实现。
- 单后端进程运行，最多 3 个 AI 调用并发，同块只能有一个活动作业。不要为该任务协调器配置多个 Uvicorn worker。进程重启后未结束作业标记 `PROCESS_INTERRUPTED`，可重试；关闭/取消会回收 CLI 进程。
- SSE 以短间隔推送持久化快照，支持句子级 Block 临时正文；前端保留 5 秒轮询兜底。作业不依赖页面保持打开，批注、历史和最终候选均存入 SQLite。
- 首版任务使用现有 `prd_agent_runs` 中的 `initial` 记录及固定请求键持久化领取，不新增表或修改已有数据库结构。编辑器打开接口以 `auto_generate: true` 请求自动启动，后端事务内判断首版资格。普通文档读取不触发生成。连续生成期间其他 AI 操作和大纲替换被阻止，人工编辑仍可保存并触发版本保护。
- 所有新接口沿用 `ActorResolver`，校验项目审批人/经理/负责人权限。部署身份模式沿用现有配置；浏览器不自行伪造身份。

后端新增依赖 `pypdf>=5,<7`、`python-docx>=1.1,<2` 和 `Pillow>=10,<13`，已列入 `backend/requirements.txt`。更新现有服务时安装后端依赖、重启后端，并刷新前端；静态前端需重新构建。本次只运行独立测试库的本机预览，没有替换现有运行服务或操作生产数据。

2026-09-12：按用户要求更新并重启本机服务。现有 `zkrai-web` 容器将 `frontend/aios-main/dist` 挂载为静态目录；重新构建后重启容器即可加载新版本。`frontend/aios-main/nginx.conf` 提供 React 路由回退，容器内配置位置为 `/etc/nginx/conf.d/default.conf`，重建容器时也应挂载或复制此配置，否则直接访问 `/prd-editor/<session_id>` 会返回 404。后端继续使用 `backend/.env` 和原有 SQLite 数据库，在 8088 端口运行。

## 代码位置

- `backend/app/models/`：五类新增持久化模型。
- `backend/app/ai/`：Provider 接口、结构化返回合同与 Codex 适配。
- `backend/app/services/block_service.py`：事务保存、历史、依赖、批注和评审快照。
- `backend/app/services/ai_service.py`：作业调度、版本保护、取消与恢复。
- `backend/app/services/document_asset_service.py`：图片与 DOCX 快照的文件存储、校验和元数据。
- `backend/app/services/docx_service.py`：Block 与 DOCX 的排版、图片/ER 图嵌入和版本化回传。
- `backend/app/api/documents.py`、`blocks.py`：文档、Block 和 SSE 接口。
- `frontend/aios-main/src/api/prd-editor/`：全屏编辑器和独立组件。

## 全文自动解决流程（2026-09-15）

- 接口 `POST /prd-documents/{document_id}/review/{review_run_id}/resolve` 创建 `document_revision` 作业；原审核必须属于当前文档且具备可读取的结构化报告。
- Provider 的 `resolve_document` 合同接收最新 Block 内容和审核问题，返回按合法 Block ID 定位的修订内容。非法模块引用、空结果、版本冲突和取消均作为明确失败处理，不静默覆盖正文。
- 后端最多执行三轮修订和复审，应用后的最后一次 `document_review` 成为新的审核基线，避免继续显示旧报告的过期提示。
- 自动修订提示词仅处理面向用户的 PRD 内容；内部 Block 编号、依赖元数据和编辑器实现说明不应写入正文。未明确的非关键实现选择采用保守默认值，并在正文中清晰记录；真正需要业务拍板的事项可留作人工决策。
