# Agent 超时预算扩展设计

## 背景

`convert_to_work_item` 的最新一次执行在单次 Codex 调用达到 900 秒后被后端终止，并被映射为 `AGENT_UNAVAILABLE`。该调用没有持久化 `response`，Codex 又以 `--ephemeral` 运行且输出位于临时目录，因此不存在可以恢复或继续消费的中间拆解结果。

## 目标

- 将后端单次 Agent 调用上限从 900 秒提高到 2000 秒。
- 为正常成功路径提供覆盖后端 Agent 调用的浏览器请求预算；不承诺覆盖所有结构化输出重试或语义修复轮次的理论总时长。
- 保留有限超时和当前失败语义，不把无结果的失败调用误认为可恢复任务。
- 同步更新运行配置、示例配置、测试和架构说明。

## 方案选择

采用分层预算：后端每次 Agent 调用 2000 秒；前端单 Agent 命令 2075 秒；前端双 Agent 命令 4150 秒。前端继续为正常成功路径中的每次后端 Agent 调用预留 75 秒的网络、数据库提交和进程清理余量。结构化输出重试或拆解语义修复会增加额外调用，故这两个前端预算并不覆盖其理论最大总时长；该长路径可返回 `REQUEST_TIMEOUT`，随后沿用现有的状态刷新和重试恢复。

不采用以下方案：

- 前端统一设为 2000 秒：双 Agent 命令会在第二次调用期间被浏览器提前取消。
- 前端取消超时：服务异常时请求可能无限挂起，用户也无法获得可重试反馈。

## 组件与数据流

后端 `Settings.codex_timeout_seconds` 的默认值和 `CODEX_TIMEOUT_SECONDS` 环境变量回退值改为 2000，`backend/.env.example` 同步展示该值。本机运行用的、未纳入 Git 的 `backend/.env` 也改为 2000；服务需要重启后才会读取新配置。

前端命令请求继续按动作分类：创建 Session 和 `message` 使用 2075 秒；`create_spec`、`revise`、`restore_spec_version`、`convert_to_work_item` 与 `publish_review` 使用 4150 秒；普通事务仍使用 130 秒。

## 失败与恢复语义

达到 2000 秒后，后端仍终止并回收 Codex 子进程，记录失败的 `AgentCall`，公开返回 `AGENT_UNAVAILABLE`。前端达到自身预算后仍返回可重试的 `REQUEST_TIMEOUT` 并重新读取 Session 状态。

只有已经持久化为 `RESULT_READY` 的完整结构化响应才可进入后续校验或物化。本次失败调用的 `response` 为空，不能续跑；配置生效后需要重新发起 `convert_to_work_item`。

## 测试与验收

- 后端配置测试断言默认超时为 2000 秒，并验证显式环境变量仍可覆盖默认值。
- 前端测试精确断言单 Agent 预算为 2,075,000 毫秒、双 Agent 预算为 4,150,000 毫秒、普通事务预算保持 130,000 毫秒。
- 更新架构说明中的预算数字和推导关系。
- 运行相关后端单元测试、前端 API 测试，并在完成前运行项目适用的完整测试集。
