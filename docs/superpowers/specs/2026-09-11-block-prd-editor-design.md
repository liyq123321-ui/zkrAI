# Block 级 AI PRD 编辑设计草案

日期：2026-09-11。状态：按用户确认直接修改现有项目代码，完成后一次验收；实现与验证记录见 `docs/block-prd-editor.md`。

用户明确本次代码修改不需要遵循 SDLC 阶段规划。下文生命周期选择表仅保留此前调查记录，不作为本次编码的前置门禁。

## 目标与范围

在现有 React + FastAPI + SQLite 工程新增 Block 编辑能力，将 PRD 编写入口改为可独立打开、刷新和返回的全屏页面。AI 正文生成、修改和审核的最小单位始终是一个 Block。结构规划只输出标题、层级、指令和依赖，不输出整篇正文。

本版包含模板/大纲导入、结构规划、逐 Block 生成、人工编辑、行范围及多 Block 批注、AI 局部修改、版本历史、Diff、冲突处理、后台任务、依赖失效标记。排除多 Agent 自主协作和多人实时协作。

## 已核实的现有结构

- `frontend/aios-main/src/App.tsx` 用路径区分页面；可以增加独立 PRD 页面分支，无需引入新的应用或路由框架。
- `ApiWorkspace.tsx` 的根任务详情嵌入 `PrdReviewPanel`；`chooseLifecycleRoute()` 目前直接调用 `create_spec`，会等待整份规格生成。新入口必须覆盖这里，不能先生成整篇再拆块。
- `PrdReviewPanel.tsx`、`PrdDocumentViews.tsx` 实现整篇阅读、Gitea Diff、逐行批注、历史与审核。其批注依赖远端 PR 的版本和行号，不适合作为频繁自动保存的草稿存储。
- `backend/app/database/models.py` 已有 `Project`、`SpecVersion`、`AgentSession`、`AgentCall`、`AgentRuntimeEvent` 等；`database.py` 统一创建 SQLAlchemy 表及 SQLite 迁移。
- `backend/main.py` 通过 `create_app()` 注入服务、身份解析器和数据库会话。新增服务与路由沿用这个入口。
- `CodexStructuredRunner.run()` 已支持独立临时工作目录、结构化输出校验和进程清理，可在新的 Provider 内复用。
- `CommandJobCoordinator` 已有后台任务和 SSE 实践，但限定任务拆分命令，并限制同一会话的活动任务。复用其设计模式，不将 Block 作业塞进该命令队列。
- 后续任务拆分读取 `SpecVersion.content` 的 `ProjectSpecPayload`，不只读取 Markdown。Block 内容提交审核时必须同步对应的结构化规格，防止下游读取旧需求。

调查基线：分支 `yq-new`，提交 `1a5245a`。本地原有 `backend/app/agents/codex.py` 和 `backend/tests/unit/test_agent_gateway.py` 修改需要完整保留。

| 方案 | 影响与取舍 |

## 模板来源与转换

已提取阿里 PDF 全部 7 页文字并检查页面；鹅厂 PDF 全部 20 页已提取文字，检查了包含主要模板的第 1–5 页。鹅厂后续写作教程中的图片案例不作为本次默认大纲。

提供两个有来源说明的内置模板，并支持导入 Markdown/纯文本大纲或文字型 PDF。默认推荐阿里模板；用户可切换鹅厂模板。模板是资料输入，里面的示例名称、人员、排期、业务和指令都不构成用户需求或执行授权。

阿里模板保留五个顶层章节：

1. 文档说明：更新记录、变更日志、名词术语表、产品说明、开发排期。
2. 产品概念设计：产品概念、功能结构、信息结构图、产品结构图、Feature List、页面流程图。
3. 全局说明：功能权限、全局交互、常用字段说明。
4. 需求说明：需求列表、需求明细、非功能需求。
5. 项目规划。

鹅厂模板保留变更记录，以及业务背景、业务场景、产品定位、服务对象、产品逻辑、信息架构、角色术语、需求列表、需求明细、非功能需求、人员与排期。原 PDF 的部分父标题位置和编号不一致，导入预览说明规范化后的父子关系，不机械信任编号。

生成 Plan 时，根据项目背景将“产品说明”细分为背景、用户问题、目标、用户场景，将“需求明细”扩展成当前项目的功能 Block；登录、搜索、支付只在该项目确实需要时出现。成功指标是本次用户要求的补充节点，不声称它是附件原始标题。

导入先展示解析出的目录；结构规划完成后验证节点、父子关系及依赖，再保存正式 Plan。每个节点只有一个稳定 block_id，重名标题也不会共用 ID。计划修订不能覆盖已有正文；有内容时导入另一模板创建独立草稿或显式合并。

文字型 PDF 导入设大小及页数限制；扫描件无法提取时返回明确提示并允许粘贴大纲，不把空解析当作成功。Markdown 解析忽略代码围栏内的伪标题。模板引用图的类型作为写作指令，不照搬案例图中的业务。

## 页面与交互

独立地址建议为 `/prd-editor/:sessionId`；“编写 PRD”通过真实链接打开新的全屏页面。页面刷新按会话恢复对应草稿，返回链接指向原项目。已有 PRD 可按原有章节拆入新草稿，保留原文和来源版本；重复打开不得重复建文档。只读正式版本通过“创建可编辑草稿”进入，原件继续只读。

顶部为专属水平大纲区域：PRD 根节点在左，章节与功能节点向右展开，提供水平滚动、选中定位和依赖连线。模板目录先出现，经过验证的规划结果与 Block 状态通过事件更新。展示真实规划和生成状态，不用延时动画伪装 AI 实时思考；轻量入场动画不阻塞编辑。

下方三栏：左侧可折叠目录与多选框；中间当前 Block 标题、指令、带行号的 Markdown 编辑及预览；右侧 AI 指令、批注、运行结果和冲突提示。沿用现有字体、颜色与按钮样式，小屏将侧栏折叠为抽屉。

新增组件：`PRDEditor`、`BlockTree`、`BlockEditor`、`BlockToolbar`、`BlockCommentPanel`、`BlockHistory`、`GenerationStatus`；大纲区域可独立为 `BlockPlanMap`。

点击节点只切换当前 Block，不触发 AI。当前块提供 AI 修改、重新生成、添加批注、查看历史、保存。批量生成只是按依赖顺序提交多个单 Block 作业。某个作业失败不阻止其他块的阅读和人工编辑。

人工编辑采用短延迟自动保存，并提供明确的未保存/保存中/已保存/保存失败状态。切换块时保留按 block_id 隔离的本地草稿，迟到的请求不能写入另一个块。关闭页面前提示未保存内容。AI 结果到达时，还要检查前端未保存草稿，不能仅因数据库版本相同就覆盖正在输入的内容。

## 数据模型

新增 `backend/app/models/` 下的五类 SQLAlchemy 模型，引用现有 Base；由现有数据库初始化入口显式导入注册。建议表名前缀 `prd_`，避免和现有版本表、评审任务混淆。

| 模型 | 主要字段与约束 |
| --- | --- |
| Document | id、project_id、session_id、title、background、global_rules、template、plan_status、revision、source_spec_version_id、created_by、时间；一份活动草稿需有数据库唯一约束。 |
| Block | id、document_id、title、parent_id、order、status、version、content、summary、instruction、dependencies、summary_version、结构化规格片段及其来源版本；ID 服务端分配。 |
| BlockVersion | id、document_id、block_id、version、content、summary、instruction、父子关系/依赖快照、修改来源、actor_id、run_id、时间；唯一键 `(block_id, version)`。 |
| BlockComment | id、document_id、text、actor_id、resolved、targets、时间；每个 target 保存 block_id、base_version、可选 start_line/end_line 和引用文字。 |
| AgentRun | id、document_id、block_id、type、status、base_version、input_snapshot、dependency_versions、document_context_revision、result、apply_status、error、request_id、时间；请求幂等和同一 Block 的活动作业约束。 |

结构规划使用 `type=plan`、`block_id=null` 的作业，仅产生结构；正文作业 `generate/revise/review` 必须有一个 block_id。`status` 使用用户指定的 queued/running/completed/failed/cancelled；结果冲突用独立的 `apply_status=conflict` 表达，不混成运行失败。

## API 与服务边界

新增 `services/block_service.py` 负责草稿、树、版本、批注、依赖、快照与原子写入；`services/ai_service.py` 负责持久化作业、调用 Provider、取消、状态通知和结果应用。

新增 `ai/provider.py` 定义可注入接口：`plan_outline()`、`generate_block()`、`revise_block()`、`review_block()`。`CodexProvider` 只包装现有 Runner，不在业务服务绑定模型，也不走旧的整篇 `rewrite_prd()`。

建议路由分组：

- `documents`：按会话创建/恢复、读取、导入大纲、提交结构规划、读取事件与作业、导出 Markdown、提交审核快照。
- `blocks`：读取与条件保存、生成/修改/审核、批注、历史与 Diff、取消作业、应用候选结果。

所有写入沿用 `ActorResolver` 和项目编辑权限。跨文档 parent、dependency、comment target、run ID 均拒绝。依赖与父子树禁止自引用、环路和缺失节点。

## AI 输入与局部修改

服务端构造固定输入白名单：当前 Block 标题、指令、当前正文、文档基本背景、相关上游的有效摘要、当前目标的反馈/批注、全局规则，以及必要的版本标识。不给 Provider 整篇文档、全部对话、任意兄弟 Block 正文或项目文件目录。

模板和用户反馈均作为带边界的业务资料传入。运行不暴露隐藏推理过程，仅发布规划、状态、最终内容、摘要和可解释的错误。

正常生成结果遵循 `block_id/base_version/content/summary/affected_blocks` 合同；后端还校验返回 ID 和版本必须等于作业记录。`affected_blocks` 仅提供标记建议，不能让模型改写其他块。

指定行范围时，先冻结所选版本与行范围，AI 修改结果只用于替换该范围；服务端验证范围外内容保持不变。一般反馈由模型尽量保留无关内容并可查看 Diff。多 Block 批注共享一条批注记录，但每个目标单独创建作业、单独捕获版本、独立成功或冲突。

## 版本冲突与结果应用

人工保存和 AI 应用都采用数据库条件更新：只有 `id` 和预期 `version` 同时匹配才写入，并在同一个事务中生成历史、增加版本及标记下游失效。禁止只在进程内先查后写。内容没有变化的重复保存不创建多余版本；状态变更和批注本身不增加内容版本。

AI 请求冻结 base_version。结果生成后先保存到 AgentRun；版本仍一致时才可应用。人工输入中的本地草稿也必须受保护。版本不一致时正文保持原样，展示“AI 结果基于旧版本生成”，提供：

- 查看 Diff：可查看 AI 基线、当前保存版和 AI 候选结果。
- 基于当前版本重新生成：创建新作业，读取当前内容及明确选择的反馈。
- 仍然应用：用户明确选择后，以当前预期版本再次条件写入；若又发生变化则继续冲突，不能使用无条件强制覆盖。

历史恢复也创建新版本，不回退版本计数。人工保存失败和冲突保留输入文本。AI 取消后即使结果迟到，也不能应用。

## 依赖、摘要与后台作业

编辑上游正文、指令或依赖后，沿反向依赖图传递标记已有下游内容为 outdated，不自动重写。尚未生成的块保持 pending，显示依赖待更新的原因。

人工编辑后旧摘要不能继续冒充当前版本摘要。保存时生成有长度上限的确定性正文摘录并标注来源；Block 审核/生成可提供更好的摘要，必须关联匹配的版本。生成默认要求上游已有有效内容和摘要，缺少依赖时给出可操作提示。

作业冻结上游版本和全局背景/规则修订号；返回时这些输入已变化，则候选结果保留并提示依赖已更新，不能显示成最新 ready 内容。多选生成按拓扑顺序排队，第一版采用有限并发，同一个块只允许一个活动正文作业。

POST 提交迅速返回 202 与 run_id。后台不持有跨越 AI 等待的数据库事务。SSE 提供文档状态快照、节点和作业更新；断线后重新读取持久化快照并恢复监听，避免重复应用。刷新和切换页面不取消后台作业。显式取消会终止 CLI 并回收进程。

首版沿用现有单服务进程部署方式；重启将未结束的作业标为 failed/PROCESS_INTERRUPTED 并允许重试，保留结果及历史。服务关闭回收任务。单进程假设记录在运行说明中，不引入外部队列或多人实时系统。

## 与既有 PRD 审核和任务拆分衔接

旧版本及其 Gitea 记录保持原样。新编写入口先建立 Block 文档；不能为了出现编辑页面先调用 `create_spec` 生成整篇正文。旧 PRD 导入仅在用户进入编辑时按标题拆块，现有结构化字段与需求 ID作为来源映射保留。

Block 草稿是编辑时的权威内容。只有用户提交审核时才冻结一组 Block 版本，按目录顺序确定性拼装 Markdown。每个语义 Block 维护对应的结构化规格片段及来源版本；人工修改导致片段过期时，只对该 Block 做结构提取/审核。随后本地合并为 `ProjectSpecPayload`，验证必需字段、需求 ID、验收引用和来源一致性。

结构缺失或过期时返回具体 Block 和原因，不偷偷使用旧规格、填造验收条款或调用 AI 兜底重写整篇。汇总验证通过后创建新的 SpecVersion，并复用现有正式评审边界；提交快照不等同于批准或开始任务拆分。新编辑器的批注修订按钮不能落回原有整篇重写调用。

本版的图表章节可保存 Markdown 和已有合法图引用；不扩展成新的通用绘图器。原有已保存图与正式版本阅读能力应通过回归测试保留。

## 验收依据

1. 导入两份模板均能看到正确的标题层级，示例业务不被写入项目事实；刷新后 block_id 稳定。
2. 页面进入不等待整篇生成；模板结构及随后 Plan 可见，节点状态按实际事件更新。
3. 生成一个块的 Provider 输入不含兄弟正文和全部历史；数据库只改变目标内容及允许的失效标记。
4. 人工编辑、自动保存、切换块和延迟响应不丢字，不把 A 块内容写进 B 块。
5. AI 使用 v5 时人工保存到 v6，结果不能覆盖；Diff、重新生成和显式应用均可用，二次竞争仍受到保护。
6. 数据库仍为 v5 但前端已有未保存输入时，同样不覆盖人工输入。
7. 行批注锚定版本，越界被拒绝；范围修改不改范围外文本；多块批注产生独立作业。
8. 历史保存完整，恢复创建新版本；重复请求不会重复作业或版本。
9. 依赖传递失效、循环检测、无效跨文档引用、过期摘要和生成期间上游变化均有测试。
10. 作业失败、取消、CLI 超时、断线重连和进程重启不会让页面锁死或写入迟到结果。
11. 新旧数据库都能初始化；现有 PRD/Gitea 审核、任务拆分以及原来的本地 Codex 修复保持兼容。
12. 后续评审和任务拆分读取与当前 Block 快照一致的规格；结构缺失时明确阻止提交。

验证采用现有 pytest、Vitest、TypeScript 检查和前端构建；用可控制延迟的假 Provider 检查并发竞争，再做真实 Codex 小 Block 联调与页面操作检查。测试数据库使用临时文件，不把开发库当测试库。
