# 任务执行引擎实施计划

> 目标：把当前「只校验不调度」的 WorkItem 依赖 DAG，改造成真正可驱动执行的调度引擎。
> 前置阅读：`docs/图引擎调研.md`（结论：依赖图完整，但缺调度层）
> 编写日期：2026-09-03

## 0. 先说清楚：现有机制给了什么，又拦着什么

动手前必须知道的四件事，每一条都直接决定实现方式。

### 0.1 已有的免费能力（改一行就能用）

| 能力 | 现成实现 | 说明 |
| --- | --- | --- |
| 幂等 | `command_id` + `input_hash` | 新动作自动获得，狂点按钮无害 |
| 乐观锁 | `expected_state_version` CAS | 并发启动两个任务，后一个自动 `STALE_STATE` |
| 租约与恢复 | `CommandAttempt` + `prepare_owner_id` | 中断可安全重试 |
| 审计 | `AuditEvent` + `ProcessedCommand` | 每次执行自动留痕 |
| 表自动创建 | `Base.metadata.create_all` | **`init_database` 最后一行**，新表无需写迁移 |

最后一条尤其省事：`database.py:41` 是 `Base.metadata.create_all(target_engine)`，所以**新增表只要在 `models.py` 定义即可，不必仿照那三个 `_migrate_sqlite_*` 写迁移**。

### 0.2 拦路的：守卫会拒绝修改 WorkItem

`command_service.py:855-889` 的 `_enforce_guard` 规定：

```python
allowed = (SpecVersion, SpecReview, ClarificationRequest, ClarificationResponse,
           WorkItem, WorkItemDependency, AgentSpec)     # 允许"新增"的类型
...
for item in db.dirty:
    if item is project or item in added: continue
    if isinstance(item, AgentCall) and item.id in allowed_agent_call_ids:
        # 仅限 changed <= {"status","completed_at"} 且 RESULT_READY → SUCCEEDED
        continue
    if isinstance(item, ReviewTask) and item.id in allowed_review_task_ids:
        # 仅限 changed <= {"new_spec_version_id","new_version"} 且原值均为 None
        continue
    raise ValueError("handler modified an existing protected row")
```

`WorkItem` 只在 `allowed`（**新增**）名单里，**不在 dirty 豁免名单里**。所以直接 `work_item.status = "in_progress"` 会当场被拒。

**这不是障碍，是设计意图在提醒你**：整个系统是 append-only 的——SpecVersion 不可变（新版本是新行）、AgentCall 追加、AuditEvent 追加。给 WorkItem 加可变状态与整体风格相悖。

### 0.3 拦路的：`PrepareContext` 没有数据库会话

```python
@dataclass(frozen=True, slots=True)
class PrepareContext:
    project_id: str
    session_id: str
    request: SessionCommandRequest
    input_hash: str
    state: SessionState        # ← 注意：SessionState 里没有 work items 信息
```

`prepare` 阶段无法直接查库。解决办法是**照抄现有 service 的模式**：`ProjectService(session_factory, agent_gateway)` —— 构造函数持有 `session_factory`，`prepare` 里自己开 session 做只读查询。

### 0.4 拦路的：`_targets` 不注册就永远失败

`_validate_result`（891 行）用 `_targets(action, before)` 校验转移合法性，查不到就返回空集，于是：

```python
if (phase, status) not in self._targets(action, before):
    raise ValueError("handler proposed an invalid workflow transition")
```

空集的 `not in` 恒为真 → **新动作必须显式注册，否则必挂**。

| 期 | 交付物 | 可独立验收 | 预估改动 |
| --- | --- | --- | --- |

### 2.1 新增 `WorkItemRun` 表

`app/database/models.py` 末尾追加：

```python
class WorkItemRun(Base):
```

三个设计点：

- **`uq_work_item_run_command` 唯一约束是幂等的第二道保险** —— 同一个 `command_id` 重试时，数据库层面就挡住了重复记账。
- **`agent_call_id` 提前留好**，P3 接 Agent 时不用改表。
- **不设"当前状态"字段**。状态由「最新一条 run」聚合得出，避免可变状态。

### 2.2 新增状态聚合与就绪计算

新建 `app/services/execution_graph.py`（纯函数，好测）：

```python
"""Derived execution state over the WorkItem dependency DAG."""

from __future__ import annotations
from collections.abc import Mapping, Sequence

RUN_TO_ITEM_STATUS = {
    "STARTED":   "in_progress",
    "SUCCEEDED": "done",
    "FAILED":    "failed",
    "BLOCKED":   "blocked",
}


def collapse_runs(runs: Sequence) -> dict[str, str]:
    """Latest run per work item wins.

    ``runs`` must be ordered by (work_item_id, created_at, id) — the caller
    guarantees this so the result is deterministic.
    """
    status_by_item: dict[str, str] = {}
    for run in runs:
        status_by_item[run.work_item_id] = RUN_TO_ITEM_STATUS.get(run.status, "todo")
    return status_by_item


def ready_work_item_ids(
    executable_ids: set[str],
    dependencies: Mapping[str, list[str]],
    status_by_item: Mapping[str, str],
) -> list[str]:
    """Executable items whose dependencies are all done and that are not done.

    Mirrors the acyclic guarantee enforced at decomposition time; a cycle
    simply yields no ready items rather than looping forever.
    """
    done = {item for item, status in status_by_item.items() if status == "done"}
    return sorted(
        item_id
        for item_id in executable_ids
        if status_by_item.get(item_id, "todo") != "done"
        and set(dependencies.get(item_id, ())) <= done
    )
```

**注意 `dependencies.get(item_id, ())`**：`QueryService._dependencies()` 只为**有依赖边**的 item 生成 key，无依赖的 item 不在字典里。用 `get(..., ())` 兜底，否则无依赖的任务永远不会被判为就绪——这是个容易踩的坑。

返回 `sorted()` 保证确定性，与 `_kahn_leftovers` 的风格一致。

### 3.4 新建 `ExecutionService`

`app/services/execution_service.py`：

```python
class ExecutionService:
    """Drive WorkItem execution across the dependency DAG."""

    ACTION_TO_RUN_STATUS = {
        CommandAction.START_TASK: "STARTED",
        CommandAction.COMPLETE_TASK: "SUCCEEDED",
        CommandAction.FAIL_TASK: "FAILED",
    }

    def __init__(self, session_factory):
        self._session_factory = session_factory

    async def prepare(self, context: PrepareContext) -> PreparedCommand:
        work_item_id = (context.request.payload or {}).get("work_item_id")
        if not work_item_id:
            raise CommandHandlerRejected("payload.work_item_id is required")

        # 友好预检：给出可读错误，不依赖 materialize 的兜底
        with self._session_factory() as db:
            self._assert_ready(db, context.project_id, work_item_id, context.request.action)

        # agent_backed=False：P1/P2 不调外部 Agent，prepare 无外部副作用
        return PreparedCommand(
            payload={"work_item_id": work_item_id,
                     "run_status": self.ACTION_TO_RUN_STATUS[context.request.action]},
            agent_backed=False,
            audit_payload={"work_item_id": work_item_id},
        )

    def materialize(self, uow, context, prepared) -> CommandHandlerResult:
        uow.add_work_item_run(WorkItemRun(
            id=_new_id(),
            project_id=context.project_id,
            work_item_id=prepared.payload["work_item_id"],
            status=prepared.payload["run_status"],
            actor_id=context.request.actor_id,
            command_id=context.request.command_id,
            note=_comments(context.request),
        ))
        # 权威校验放在事务内，防 prepare→materialize 之间的状态漂移
        self._assert_ready(uow.session, context.project_id,
                           prepared.payload["work_item_id"], context.request.action)
        return CommandHandlerResult(
            phase=None, spec_status=None,
            created_resource_ids=[],
            audit_payload={"work_item_id": prepared.payload["work_item_id"],
                           "run_status": prepared.payload["run_status"]},
        )
```

四个要点：

1. **`prepare` 做友好预检，`materialize` 做权威校验。** 两次都要——prepare 的错误能变成给用户看的提示，materialize 的校验才是正确性保证（两者之间状态可能已变）。
2. **`agent_backed=False`。** P1/P2 不调 Agent，prepare 无外部副作用，租约窗口极短。
3. **`CommandHandlerResult` 的 `phase` / `spec_status` 均为 `None`**，因此 `_apply` 不改工作流状态，只有 `state_version` 递增（由 `_advance_project` 自动完成）。前端据此刷新。
4. **materialize 里抛异常 → 整个事务回滚**，run 不会落库，且 `_record_failure` 会写 `COMMAND_HANDLER_FAILED` 审计。

`_assert_ready` 的校验规则：

```python
START_TASK    → 该 item 必须 executable，且 status 为 todo，且所有依赖已 done
COMPLETE_TASK → 该 item 当前 status 必须为 in_progress（最新 run 是 STARTED）
FAIL_TASK     → 同上
```

不满足就抛 `CommandHandlerRejected`（会走 `_reject_attempt` 分支，写 rejection 审计而非 failure，语义更准）。

## 5. P3：自动执行（有硬性前置）

### 5.1 为什么 P3 不能直接做

`command_service.py:352-356` 的注释写得毫不含糊：

```python
# Preparation leases are process-local by design.  The deployment is
# explicitly single-process; durable owner IDs make abandoned leases
# diagnosable while AgentCall checkpoints determine safe recovery.
_ACTIVE_PREPARATIONS: ClassVar[dict[str, str]] = {}
```

P1/P2 的 prepare 是**纯本地校验**（毫秒级），租约窗口极短，单进程完全够用。

但 P3 的 prepare 要**调 Agent 真跑任务**，租约会持有几十秒到十几分钟。此时多实例部署会出现：两个实例同时持有同一 `attempt_id` 的租约，各自调一次 Agent，产生两条 `AgentCall`，浪费算力且可能重复副作用。

### 5.2 P3 前置任务：租约外置

把 `_ACTIVE_PREPARATIONS` 换成分布式锁。最省事的做法是**复用数据库**（无需引入 Redis）：

```python
def _register_preparation(cls, attempt_id: str, owner_id: str) -> bool:
    # INSERT INTO command_attempts(...) ON CONFLICT DO NOTHING
    # 或用 SELECT ... FOR UPDATE 的行锁，按 attempt_id 串行化
```

要点：
- 用 `attempt.prepare_owner_started_at` 做**超时判定**（现有字段已存在，不必加列）
- 心跳续约沿用 `project_service.py` 里 `IntakeAnalysisClaim` 的模式（30s 租约 / 5s 心跳），那套代码已经跑通了，直接照搬

### 5.3 P3 本体

`ExecutionService.prepare` 改为：

1. 校验就绪（同 P1）
2. 通过 `AgentGateway` 新增一个 `execute_task(agent_spec, ...)` 方法，调 Codex CLI 跑任务
3. 落 `AgentCall`（走现有的 `_record_call_result` / `_record_call_failure`）
4. 返回 `PreparedCommand(agent_backed=True, agent_call_ids=[call.id], ...)`
5. `materialize` 里写 `WorkItemRun` 时带上 `agent_call_id`

前端超时从 `STANDARD` 改到 `SINGLE_AGENT`（975s）。

`agent_call_id` 字段在 P0 已经预留，无需改表。

## 6. 风险与决策记录

| # | 决策点 | 选定方案 | 备选及放弃理由 |
| --- | --- | --- | --- |
| 1 | 状态存哪 | 新增 `work_item_runs` append-only 表 | 直接改 `WorkItem.status`：会被 `_enforce_guard` 拒绝，需给守卫开豁免口子，且引入可变状态与系统风格冲突 |
| 2 | 依赖校验时机 | prepare 预检 + materialize 复检 | 只在一处：prepare 的数据可能过期；只在 materialize：错误反馈差（事务回滚，拿不到友好提示） |
| 3 | per-item 动作如何下发 | 后端算好塞进 `available_actions` | 前端自行推导：违反「前端只渲染 legal_actions」的核心纪律 |
| 4 | P1/P2 是否调 Agent | 不调 | 调：会撞上 process-local 租约限制，且无法回退 |
| 5 | 新表如何迁移 | 靠 `create_all`，不写迁移函数 | 写 `_migrate_sqlite_*`：新表无需迁移旧数据，`create_all` 已在 `init_database` 末尾 |

### 三个必须注意的坑

1. **`dependencies.get(item_id, ())` 必须兜底。** `QueryService._dependencies()` 只为有依赖边的 item 生成 key，漏了 `get` 会导致无依赖的任务永远不被判为就绪。
2. **`workItemLane()` 必须补 `failed`。** 现有实现不认识该状态，会静默归到 `todo`。
3. **`_targets` 必须注册，否则 `_validate_result` 恒失败。** 空集的 `not in` 永远为真，报错信息还是 "invalid workflow transition"，极具误导性。

## 7. 执行顺序建议

```
P0 → 跑全量测试确认无回归 → P1 → 补单测 → P2 → 手测 UI → (决策点：要不要自动化) → P3
```

P0 完成后就能在 UI 上看到 `available_actions`，可以先人工核对"系统认为哪些任务可开始"是否符合直觉，**在写任何执行逻辑之前先验证图算得对**。这一步很便宜，但能提前暴露依赖图本身的问题。

P2 结束时，你已经有了一个完整可用的「人工驱动的任务执行看板」。此时可以暂停，用它跑几个真实项目，看看依赖模型是否经得起实践检验——**再决定是否值得投入 P3 的自动化**。我建议这么做：P3 的成本主要不在代码，而在分布式锁和 Agent 执行的可靠性，而这套依赖模型本身还没被真实使用验证过。
