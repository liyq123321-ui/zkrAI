## 0. 结论先行

**后端没有采用任何图引擎框架。**

但工程里确实存在一张真正意义的有向图 —— **WorkItem 依赖 DAG**。它的定位是：

> **它是流水线的「产物」和「校验对象」，不是流水线的「执行引擎」。**

一句话概括三者的关系：

| 层 | 是什么 | 用什么实现 | 是否是图引擎 |
| --- | --- | --- | --- |
| 工作流控制流 | 有限状态机 FSM | 两张查表 `ACTION_TABLE` / `NEXT_ACTION_TABLE` | ❌ 不是图 |
| Agent 编排 | 硬编码顺序流水线 | Python 函数直调 + 重试循环 | ❌ 不是图 |
| **任务依赖图** | **有向无环图 DAG** | **自建邻接表 + Kahn 算法** | ⚠️ **是图，但只校验不调度** |

真正驱动系统运转的是**状态机 + 两阶段命令引擎**；任务依赖图在流水线的最后一环被生产出来，落库、投影、展示，然后**停在那里** —— 没有任何代码遍历它去驱动执行。

## 2. 真正的执行控制流：有限状态机，不是图

系统真正的"运转逻辑"在 `app/domain/workflow.py`（113 行），是**纯查表的 FSM**：

```python
ACTION_TABLE: dict[tuple[ProjectPhase, SpecStatus], tuple[CommandAction, ...]]
NEXT_ACTION_TABLE: dict[tuple[ProjectPhase, SpecStatus], str]
```

输入是一个二元组 `(ProjectPhase, SpecStatus)`：

- `ProjectPhase`（6 态）：`INTAKE` / `NEED_CLARIFICATION` / `SPECIFICATION` / `REVIEW` / `DECOMPOSITION` / `AGENT_SPECS_READY`
- `SpecStatus`（7 态）：`DRAFT` / `AUTO_REVIEW` / `HUMAN_REVIEW` / `APPROVED` / `REWORK` / `NEED_CLARIFICATION` / `REJECTED`

输出两个东西，由 `state_projection.project_state()` 下发给前端：

- `legal_actions` —— 当前**允许**执行的动作集合
- `next_action` —— 建议的下一步（如 `ANSWER_CLARIFICATION` / `CREATE_SPEC` / `HUMAN_REVIEW` / `CONVERT_TO_WORK_ITEM` / `NONE`）

**前端严格只渲染 `legal_actions`，不自行推导。** 这是整个架构最重要的一条纪律。

### 为什么它是 FSM 而不是 DAG

- 状态可以**回环**：`REVIEW + REWORK → (REVIEW, REWORK)` 可以反复返工；`publish_review` 生成新版本又回到 `HUMAN_REVIEW`。DAG 不接受回边。
- 转移由**人类决策**驱动（approve / reject / rework / publish_review），不是由节点完成事件自动触发。
- 状态是**单例**（一个 project 在某一时刻只有一个 phase + 一个 spec status），不是多节点并发的图。

用图引擎（如 LangGraph）建模反而不合适 —— 你真正需要的是「状态 + 守卫 + 人工中断」，这正是 FSM 的强项。

## 3. 真正的图：WorkItem 依赖 DAG

这是工程里唯一的真图。以下是它的完整生命周期。

### 3.1 图的形状：一棵三层树 + 一组跨层依赖边

```
                        ROOT (local_key="root", executable=False)
                                     │
                    ┌────────────────┼────────────────┐
              MILESTONE-1      MILESTONE-2      MILESTONE-3
              (parent=root)    (parent=root)    (parent=root)
                    │                │                │
            ┌───────┴──────┐        ...              ...
         TASK-A         TASK-B
      (parent=M-1)    (parent=M-1)
            │  ▲
            └──┘  ← 依赖边（可跨 milestone、可跨层）
```

**树的部分**（`parent_id` 外键）强约束：
- `MILESTONE` 必须顶层（`parent_key is None`），否则 `INVALID_PARENT`
- `TASK` 必须是 `MILESTONE` 的叶子子节点，否则 `UNKNOWN_PARENT` / `INVALID_PARENT`
- `local_key` 全局唯一，否则 `DUPLICATE_LOCAL_KEY`

**图的部分**（`work_item_dependencies` 表）松约束：任意两个 work item 之间可以连边，只要不成环。

### 3.2 边的表示：反向存储

`backend/app/database/models.py:246`

```python

    __tablename__ = "work_item_dependencies"
    __table_args__ = (UniqueConstraint("project_id", "from_work_item_id",
```

**方向语义：`from → to` 意为「from 依赖 to」，即边指向前置任务。**

这一点在读 Kahn 实现时极易看错 —— 代码里变量叫 `inbound`，但存的是「我依赖几个」，即**出度**。命名与 `from→to` 的方向是相反的，算法上自洽（剥掉的是"不依赖任何人"的节点），但读代码时要留意。

领域侧（`app/domain/types.py:266`）用符号引用，落库时才翻译成真实 ID：


### 3.3 图的校验：五道前置闸门

在 `validate_breakdown()`（`decomposition_service.py:224`）中，依赖图相关校验分五步，**全部在开数据库事务之前完成**：

```python

    _error("DUPLICATE_DEPENDENCY", proposal.local_key, "dependency keys must be unique")

    _error("INVALID_DEPENDENCY", proposal.local_key, "dependency key must not be blank")

# ③ 依赖键必须指向本批次提案（防止引用不存在的节点）
```

**设计意图很明确**：LLM 输出不可信，所以「开事务之前就把不安全的模型输出全部拒掉」。宁可多写一遍校验，也不让一个带环的图进入事务再回滚。

### 3.4 图算法精读（100 行，无递归、确定性输出）

#### `_kahn_leftovers`（175-189 行）

```python
def _kahn_leftovers(edges: Mapping[str, set[str]]) -> set[str]:
    """Run iterative Kahn topological reduction and return only its unprocessed keys."""
    inbound = {key: len(dependencies) for key, dependencies in edges.items()}
    successors = {key: set() for key in edges}
    for item, dependencies in edges.items():
        for dependency in dependencies:
            successors[dependency].add(item)          # 反向邻接表：谁依赖我
    ready = deque(sorted(key for key, count in inbound.items() if count == 0))
    while ready:
        key = ready.popleft()
        for successor in sorted(successors[key]):
            inbound[successor] -= 1
            if inbound[successor] == 0:
                ready.append(successor)
    return {key for key, count in inbound.items() if count > 0}
```

三个工程细节：

1. **只返回"没剥掉的节点"，不返回拓扑序。** 系统不需要拓扑序（因为没有调度器），只需要知道"是否有环"。返回值 = 环成员 ∪ 环的下游节点。
2. **全程迭代 + `deque`，无递归。** 避免深图爆栈。
3. **两处 `sorted()` 是刻意的。** 保证处理顺序与输入字典顺序无关 —— 虽然返回值是集合不受影响，但为下一步的确定性报错打了基础。

#### `_cycle_participant_iterative`（192-221 行）

Kahn 的 leftovers 里混着「真成环的节点」和「被环堵住的无辜下游节点」，直接拿 leftovers 报错会指错人。这个函数用 **DFS 三色标记**精确抓出一个真环成员：

```python
state = {key: 0 for key in edges}          # 0=未访问 1=在栈中 2=已完成
for start in sorted(candidates):
    if state[start] != 0: continue
    path, position = [start], {start: 0}
    state[start] = 1
    frames = [(start, iter(sorted(edges[start])))]      # 显式栈，非递归
    while frames:
        key, iterator = frames[-1]
        try:    dependency = next(iterator)
        except StopIteration:
            state[key] = 2; position.pop(key, None); path.pop(); frames.pop(); continue
        if dependency not in candidates: continue       # 跳过非环候选
        if state[dependency] == 1:                      # ← 回边！找到环
            return min(path[position[dependency]:])     # 环路径上字典序最小者
        if state[dependency] == 0:
            state[dependency] = 1
            position[dependency] = len(path)
            path.append(dependency)
            frames.append((dependency, iter(sorted(edges[dependency]))))
raise RuntimeError("Kahn reported a cycle but no cycle participant was found")
```

两个值得学的设计：

- **显式栈 DFS**（`frames` 存迭代器）代替递归 —— 同样是防爆栈，且比递归版好调试。
- **`return min(path[position[dependency]:])`** —— 从环路径里取**字典序最小**的 key，而不是"最先发现的那个"。这让报错信息**完全确定**：不管字典遍历顺序如何，同一个环永远报同一个 key。对写断言测试至关重要。
- 最后那句 `raise RuntimeError` 是**不可达断言**：Kahn 说有环就一定抓得到环成员，抓不到说明算法本身有 bug，直接崩比静默错好。

### 3.6 图的三重冗余存储（刻意为之）

同一份依赖信息存了三处：

| # | 位置 | 形态 | 用途 |
| --- | --- | --- | --- |
| 1 | `work_item_dependencies` 表 | 关系边 | 图谱查询、图算法 |
| 2 | `agent_specs.dependency_work_item_ids` | JSON 列 | AgentSpec 一级字段 |
| 3 | `agent_specs.content["dependency_work_item_ids"]` | 内嵌 JSON | `content_hash` 参与哈希 |

**为什么冗余？** 因为 `AgentSpec` 是发给下游 Agent 的**自包含任务书**。下游 Agent 拿到 spec 内容就应该知道"我要等谁"，不需要回查数据库。而第 3 处参与 `_canonical_hash(content)` 计算（`decomposition_service.py:379`）—— 依赖变了，spec 的内容哈希就变，因此能被 `AgentCall` 绑定和审计追踪。

这是**快照不可变性**设计，不是疏忽。

### 3.7 图的读出与投影

`query_service._dependencies()`（367-380 行）：

```python
@staticmethod
def _dependencies(db: Session, project_id: str) -> dict[str, list[str]]:
    result: dict[str, list[str]] = {}
    for edge in (db.query(WorkItemDependency)
                   .filter_by(project_id=project_id)
                   .order_by(WorkItemDependency.from_work_item_id,
                             WorkItemDependency.to_work_item_id,
                             WorkItemDependency.id)
                   .all()):
        result.setdefault(edge.from_work_item_id, []).append(edge.to_work_item_id)
    return result
```

`order_by` 三重排序保证**投影稳定**（相同数据永远产出相同顺序），这对前端渲染和快照哈希都重要。

投影结果塞进 `WorkItemRead.dependency_work_item_ids`（413 行），随 `GET /sessions/{id}/work-items` 下发。

## 4. 图在哪里断了：一份消费链断层分析

```
                    ↓
```

### 断层 ⑦ 的三个硬证据

**证据 1：依赖边在整个后端只被读一次，且只为了投影。**

全量 grep `dependency_work_item_ids | WorkItemDependency`，命中点只有：

- `models.py` — 定义
- `decomposition_service.py` — 写入（3 处）
- `command_service.py` — UOW 守卫（2 处）
- `query_service.py` — 读出投影（5 处）

**没有任何一处遍历图做调度、排序、就绪判定或状态传播。**

**证据 2：`work_items.status` 是全系统的死字段。**

列定义（`models.py:229`）：`status = Column(String, nullable=True, default="todo")`

`_work_item()` 构造函数（`decomposition_service.py:773-780`）传入的字段是：`id` / `session_id` / `project_id` / `local_key` / `parent_id` / `kind` / `executable` / ... —— **没有 `status`**，所以永远是默认值 `"todo"`。

对整个 `app/` 做 `.status =` 写入点扫描，命中的全是 `SpecVersion.status` / `AgentCall.status` / `ReviewTask.status` / `CommandAttempt.status` / `IntakeAnalysisClaim.status`，**没有一个是 WorkItem**。

**证据 3：前端泳道算法因此永远落在同一格。**

```ts
// workflowUi.ts:96
export function workItemLane(status: string | null | undefined): WorkItemLane {
  const normalized = (status ?? 'todo').trim().toLowerCase().replace(/[\s-]+/g, '_');
  if (['done','completed','complete','success','succeeded','closed'].includes(normalized)) return 'done';
  if (['in_progress','active','running','processing','in_review','review','blocked'].includes(normalized)) return 'in_progress';
  return 'todo';
}
```

前端这套泳道逻辑写得相当完备（映射了 15 种状态别名、识别 `blocked` 为"进行中"），但**后端永远不会产出 `todo` 以外的 status**，所以所有工作项永远躺在"待开始"列。

测试文件 `workspace.test.tsx` 里那些 `'in_progress'` / `'completed'` 状态是**手写的 fixture**，不是后端真能产出的值。

### 这个断层的性质

**不是 bug，是阶段边界。**

`README.md` 把定位写得很清楚：**firstFlight 第一阶段是"需求澄清、PRD 人工审核和任务拆解工作台"**。

拆解（Decomposition）是第一阶段的**终点**，不是第二阶段的起点。系统生产出一张经过严格校验、可审计、自包含的任务依赖图，交给人类/下游系统去执行 —— 它自己不执行。

两个佐证：

1. `WorkItem.executable` 字段已经埋好了：`executable=proposal.kind is WorkItemKind.TASK`（`decomposition_service.py:780`）。只有 TASK 可执行，MILESTONE 和 ROOT 不可执行。**这是未来调度器的天然入口**，但当前无人消费。
2. `AgentSpec` 的 20+ 个字段（`allowed_tools` / `allowed_paths` / `test_obligations` / `fixed_constraints` / `required_skills`…）完全是给"执行者"读的。系统精心生产了一份执行合同，但**还没有签约的乙方**。

## 5. 对照：如果它用了图引擎，会是什么样

为了把"没有图引擎"讲得更具体，列一个对照：

| 能力 | LangGraph 等图引擎提供 | firstFlight 当前实现 |
| --- | --- | --- |
| 节点注册 | `@node` 装饰器 / `add_node()` | 无。6 个 `AgentGateway` 方法手工直调 |
| 边与路由 | `add_edge()` / `add_conditional_edges()` | 无。控制流写在 Python 函数体里 |
| 共享状态 | `State` TypedDict 在节点间流转 | 无。每次调用显式组装 payload |
| 检查点 | `checkpointer` 自动持久化中间态 | 手写 `AgentCall` 表 + `ReviewTask` 表 |
| 中断恢复 | `interrupt()` / 人类介入 | 手写 `expected_state_version` 乐观锁 + `CommandAttempt` 租约 |
| 重试 | `RetryPolicy` | 手写：Codex 3 次重试 + 拆解 2 轮修复 |
| 循环 | 原生支持回边 | FSM 用 `REVIEW+REWORK` 自环表达 |
| 可视化 | `get_graph().draw_mermaid()` | 无 |

**值得注意**：右侧"手写"的每一项都实现了左侧的能力，而且做得更贴合业务（比如 `expected_state_version` 这个乐观锁，是通用图引擎不会给你的）。**这是个合理的取舍** —— 引入 LangGraph 会增加一个重型依赖，换来的调度能力在第一阶段用不上，反而要跟它的状态模型打架。

## 6. 如果要让依赖图真正"转"起来，需要补什么

假设第二阶段要让这张 DAG 驱动真实执行，最小改动清单：

### 6.1 补全状态机（必须）

当前 `WorkItem.status` 是死字段。需要：

- 定义生命周期：`todo → ready → blocked → in_progress → review → done / failed`
- 新增命令动作：`START_TASK` / `COMPLETE_TASK` / `FAIL_TASK`，注册进 `ACTION_TABLE`
- **关键**：把状态推进纳入现有两阶段命令引擎，复用 `command_id` 幂等 + `expected_state_version` 乐观锁

### 6.2 加一个就绪判定器（核心）

复用现成的 `_kahn_leftovers`，但这次**要拓扑序**而不是 leftovers：

```python
def ready_tasks(edges, done: set[str]) -> list[str]:
    """入度为 0 且所有前置已完成 → 就绪"""
    return sorted(
        key for key, deps in edges.items()
        if key not in done and deps <= done
    )
```

每完成一个任务，重算一次就绪集 —— 这就是一个最小的调度器。

### 6.3 让 `executable` 字段生效

`executable = (kind is TASK)` 已经埋好了。调度器只需过滤 `WHERE executable = true`，天然跳过 ROOT 和 MILESTONE。

### 6.4 前端补真正的连线渲染

当前 `ff-flow-canvas` 只按 kind 分列。要画真 DAG 需要：

- 用 `dependency_work_item_ids` 构造边集（数据已经下发，前端不用改后端）
- 引入轻量布局（dagre / elkjs）或直接改用拓扑层级分列 —— 后者改动更小，把 `hierarchyColumns` 的分组依据从 `kind` 换成"拓扑深度"即可

### 6.5 注意单点约束

`command_service.py` 的准备租约 `_ACTIVE_PREPARATIONS` 是 **process-local** 字典，源码注释明确写了 "deployment is explicitly single-process"。要并发执行多个 TASK，必须先把租约换成分布式锁（Redis / 数据库行锁），否则多实例会互相踩踏。
