## 2. 业务背景与产品概述

### 2.1 业务背景

个人或小型团队需要以较低部署成本管理项目、任务和进度，同时验证 Agent 从需求分析、数据模型、前后端开发、API 设计到自动化测试的完整交付能力。现有目标聚焦功能完整性、代码结构和可运行性，不追求企业级协作与权限复杂度。

### 2.2 产品目标

| 目标 | 产品能力 | 成功口径 |
| --- | --- | --- |
| 统一管理项目与任务 | 项目和任务 CRUD | 登录用户可完成创建、查询、编辑、删除闭环 |
| 直观看到进度 | 三列 Kanban 和状态持久化 | 状态变更后卡片换列，刷新后仍保持 |
| 提供基础协作属性 | 负责人、优先级、截止日期、标签 | 字段可保存、读取和编辑 |
| 快速掌握概况 | 项目任务统计 | 总数、三状态数量和 High 数量准确 |
| 可重复本地交付 | Compose、README、自动化测试 | 干净环境可完成核心链路并执行测试 |
| 保持最小安全边界 | 登录与项目级用户隔离 | 未登录返回 401，无权访问返回 403 |

### 2.3 产品定位

面向个人和不超过 5 人的小型团队，提供可在本机一键启动的轻量任务管理 MVP。产品覆盖基础项目/任务管理、三状态看板和统计，不替代企业项目管理平台，也不提供复杂协作、审批、通知或细粒度 RBAC。

### 2.4 用户角色与核心场景

| 角色 | 核心目标 | 典型操作 |
| --- | --- | --- |
| 已登录用户 | 管理自己有权访问的项目 | 登录、创建项目、查看项目列表、编辑或删除项目 |
| 项目创建者 | 管理项目中的任务 | 创建任务、分配负责人、调整状态、查看统计 |
| 任务负责人 | 明确工作归属 | 在已有访问权限前提下查看和处理被分配任务 |
| 验收人员 | 验证本地可运行和接口契约 | 使用测试用户登录、执行核心流程和自动化测试 |

### 2.5 MVP 范围

| 本期包含 | 本期不包含 |
| --- | --- |
| 简单登录认证（如 JWT） | OAuth、SSO、第三方身份提供商 |
| 项目 CRUD 和项目列表/详情 | 项目成员邀请与管理流程 |
| 任务 CRUD、负责人、优先级、截止日期、标签 | 评论、附件、子任务、工时 |
| Todo / In Progress / Done 看板 | 自定义工作流和自定义状态 |
| 项目任务统计 | 企业级报表与数据仓库 |

| Docker Compose 本地启动 | Kubernetes、云服务、复杂 CI/CD |
| 自动化 API/单元测试 | 实时协作、消息推送 |

## 3. 产品概念设计

### 3.1 产品逻辑

登录 → 查看项目列表 → 创建或进入项目 → 查看统计与 Kanban → 创建任务 → 编辑任务字段或状态 → 持久化到 PostgreSQL → 刷新后重新查询并展示。

所有项目、任务和统计请求都必须经过身份认证和项目访问检查。任务负责人关系不等于项目访问授权；MVP 不通过“被分配任务”自动扩大访问范围。

### 3.2 功能结构

| 一级模块 | 二级功能 | 说明 | 优先级 |
| --- | --- | --- | --- |
| 账号 | 登录与会话 | 提供确定性测试账号或初始化方式 | P0 |
| 项目 | 列表、详情、创建、编辑、删除 | 项目创建者自动获得管理权限 | P0 |
| 任务 | 创建、查看、编辑、删除 | 完整维护任务基础字段 | P0 |
| 看板 | 三列展示、状态变更 | 状态变更落库并换列 | P0 |
| 统计 | 总数、分状态、High 数量 | 与项目当前任务集一致 | P0 |
| 平台 | REST API、校验、错误处理 | 提供稳定状态码和 JSON 错误结构 | P0 |
| 工程 | Migration、Compose、README、测试 | 支持干净环境复现 | P0 |

### 3.3 信息结构

| 页面 | 主要信息 | 主要操作 |
| --- | --- | --- |
| 登录页 | 登录标识、密码、错误反馈 | 登录 |
| 项目列表 | 项目名称、摘要、更新时间 | 新建、进入、编辑、删除 |
| 项目详情 | 项目信息、统计卡片、Kanban | 管理项目、创建任务、切换状态 |
| 任务编辑弹窗/页 | 标题、描述、负责人、优先级、截止日期、标签、状态 | 保存、取消、删除 |

### 3.4 领域关系模型

[ER 图：用户、项目与任务核心关系](#firstflight-er-task-manager-domain-model-273edf5e)

| 实体 | 关键字段 | 关系与约束 |
| --- | --- | --- |
| User | id、login、passwordHash、createdAt | 可创建多个 Project；可被多个 Task 引用为负责人 |
| Project | id、name、description、creatorId、createdAt、updatedAt | 必须有创建者；包含多个 Task |
| ProjectAccess | userId、projectId、accessLevel | MVP 至少记录创建者对项目的管理访问 |
| Task | id、projectId、title、description、assigneeId、priority、status、dueDate、tags、createdAt、updatedAt | 必须归属一个 Project；assignee 必须是系统用户 |

### 3.5 页面与状态流

| 对象 | 初始状态 | 允许变化 | 持久化要求 |
| --- | --- | --- | --- |
| 登录会话 | 未登录 | 登录成功 → 已登录；凭证失效 → 未登录 | 会话或 JWT 可被后端验证 |
| Task.status | Todo | Todo ↔ In Progress ↔ Done | 每次有效变更写入 PostgreSQL |
| Task.priority | Low / Medium / High | 三个枚举值之间变更 | 非法枚举由后端拒绝 |
| 编辑表单 | 未修改 | 编辑中 → 保存成功 / 校验失败 / 取消 | 保存成功后更新时间变化 |

## 4. 全局业务规则

### 4.1 权限矩阵

| 操作 | 未登录 | 已登录且无项目权限 | 项目创建者/有管理权限用户 |
| --- | --- | --- | --- |
| 登录 | 允许 | 不适用 | 不适用 |
| 查看项目/任务 | 401 | 403 | 允许 |
| 创建项目 | 401 | 允许 | 允许 |
| 编辑、删除项目 | 401 | 403 | 允许 |
| 创建、编辑、删除任务 | 401 | 403 | 允许 |
| 查看统计 | 401 | 403 | 允许 |

### 4.2 字段规则

| 字段 | 类型 | 必填 | 规则 |
| --- | --- | --- | --- |
| Project.name | string | 是 | trim 后不能为空 |
| Task.title | string | 是 | trim 后不能为空 |
| Task.description | string | 否 | 普通文本 |
| Task.assigneeId | resource id | 否 | 非空时必须引用现有 User |
| Task.priority | enum | 是 | 仅 Low、Medium、High |
| Task.status | enum | 是 | 仅 Todo、In Progress、Done |
| Task.dueDate | date | 否 | 必须是合法日期格式 |
| Task.tags | string[] | 否 | 空数组合法；具体数量和长度由实现记录 |
| createdAt / updatedAt | datetime | 系统生成 | 创建时同时生成；更新时 updatedAt 刷新 |

### 4.3 REST API 与错误约定

| 场景 | HTTP 状态 | 最小响应约定 |
| --- | --- | --- |
| 创建成功 | 201 | 返回已创建资源 JSON |
| 查询、更新成功 | 200 | 返回资源或结果 JSON |
| 删除成功 | 204 | 无响应体 |
| 未认证 | 401 | `{ code, message }` |
| 已认证但无权限 | 403 | `{ code, message }`，不得泄露资源内容 |
| 字段缺失、格式或枚举非法 | 400 | `{ code, message, field_errors? }` |
| 格式合法但资源不存在或已删除 | 404 | `{ code, message }` |
| 未预期服务错误 | 500 | 安全错误结构，不泄露堆栈或敏感配置 |

资源 ID 的“格式非法”和“格式合法但不存在”必须分别按 400、404 处理，并在 API 契约和测试中保持一致。

### 4.4 删除与统计规则

- 删除项目或任务后，再次查询该资源必须返回 404。
- 项目删除时关联任务的处理方式必须由数据库约束或事务明确实现，不得留下可读取的孤儿任务。
- 项目统计从当前可访问的任务数据计算，至少包含 total、todo、inProgress、done、highPriority。
- 同一个任务只能计入一个状态桶；High 数量与状态数量相互独立。

### 5.2 关键功能明细

#### 5.2.1 登录与隔离（FR-001）

- README 必须提供可重复的测试用户初始化、快速注册或凭证注入步骤及预期结果。
- 未登录访问受保护 API 返回 401。
- 已登录用户请求无权项目或任务返回 403，不返回资源字段。
- 项目创建成功后，创建者自动获得访问和管理权限。

#### 5.2.2 项目管理（FR-002）

用户可创建、查看列表、查看详情、编辑和删除有权限项目。列表只包含当前用户有权访问的项目。项目详情集成统计和 Kanban 入口；删除后列表移除项目，后续详情查询返回 404。

#### 5.2.3 任务管理（FR-003、FR-004）

用户可在有权限项目中创建、查看、编辑和删除任务。后端必须保存全部规定字段并自动维护时间戳。负责人必须引用系统用户，但负责人关系不替代项目访问授权。

#### 5.2.4 Kanban（FR-005）

看板固定三列。状态变更成功后，前端立即将任务移动到目标列；后端持久化新状态。刷新页面或重新调用查询 API 后，任务仍位于目标列。非法状态值返回 400 且不得写库。

#### 5.2.5 项目统计（FR-006）

统计结果必须与同一事务视图或一致查询下的任务集合匹配。创建、删除或改变任务状态/优先级后，刷新统计应反映最新数据。

## 7. 验收方案

### 7.1 核心端到端路径

在干净环境启动系统 → 初始化测试用户 → 登录 → 创建项目 → 创建任务 → 修改任务状态 → 刷新页面 → 查看 Kanban 和统计 → 删除任务与项目 → 验证 404。

### 7.2 验收用例

| 用例 | 关联需求 | 输入 / 操作 | 预期输出 |
| --- | --- | --- | --- |
| TC-001 | FR-001 | 按 README 初始化用户并登录 | 登录成功；受保护 API 可访问 |
| TC-002 | FR-001、NFR-003 | 未认证请求受保护资源 | 401 + 约定错误 JSON |
| TC-003 | FR-002 | 创建、查询、编辑、删除项目 | 状态码依次符合 201/200/200/204，删除后 404 |
| TC-004 | FR-003、FR-004 | 创建并编辑含完整字段的任务 | 全部字段可读取，updatedAt 随编辑更新 |
| TC-005 | FR-005 | Todo → In Progress → Done，刷新页面 | 任务按目标列展示且状态持久化 |
| TC-006 | FR-006 | 准备已知状态和优先级任务集 | total、三状态、High 数量准确 |
| TC-007 | FR-007 | 绕过前端直接调用各 REST API | 状态码、字段和数据一致 |
| TC-008 | FR-008 | 提交空名称/标题、非法枚举、非法日期、非法 ID | 400 + 错误 JSON，不写入无效数据 |
| TC-009 | FR-009 | 查询不存在或已删除的合法 ID | 404 + 错误 JSON |
| TC-010 | FR-010 | 重启容器并刷新页面 | 用户、项目、权限关系和任务仍可查询 |
| TC-011 | NFR-003 | 用户 B 访问用户 A 的项目和任务 | 403 且不泄露内容；仅设为负责人也不扩大权限 |
| TC-012 | FR-011 | 执行 README 测试命令 | CRUD、状态、校验、权限、404、统计用例全部通过 |
| TC-013 | FR-012、NFR-001 | 干净环境执行 Compose 启动 | 三个服务健康，前端可调用后端完成核心路径 |
| TC-014 | NFR-002 | 审查依赖和基础设施 | 未引入 Kubernetes、云服务、复杂 RBAC 等范围外能力 |

### 7.3 验收准出

- TC-001 至 TC-014 全部通过，无阻断核心流程的错误。
- 前端、后端、PostgreSQL 可由 Docker Compose 启动并互通。
- 数据校验由后端实施，不依赖前端单独保证。
- 双用户隔离、状态持久化、统计一致性均有自动化证据。
- README 能让另一位审核人从干净环境独立复现。

## 9. 项目计划与责任

### 9.1 交付节奏

采用已确认的阶段重叠瀑布路线：先锁定核心需求；需求、设计、开发和测试可在已评审基线下有限重叠；每 2–4 周形成可用增量。团队不超过 5 人、周期不超过 2 个月均为规划假设，不代表已配置资源或承诺日期。

| 增量 | 建议范围 | 准出条件 |
| --- | --- | --- |
| 增量 1 | 登录、数据模型、项目 CRUD、基础权限 | 项目链路和双用户隔离通过 |
| 增量 2 | 任务 CRUD、Kanban、状态持久化、统计 | 核心端到端路径通过 |
| 增量 3 | 校验、错误处理、测试、README、Compose 优化 | 全部验收用例可重复执行 |

### 9.2 责任边界

owner-1 是现有证据中的项目经理与最终审核人，负责范围、关键决策和准出确认。具体前端、后端、测试和数据库执行人员由项目实施记录分配；本文不虚构人员或已完成状态。

## 10. 风险与决策记录

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 基础隔离实现遗漏 | 越权读取或修改 | 所有资源查询带用户/项目权限条件，增加双用户测试 |
| “负责人”被误当作权限 | 意外扩大访问面 | 明确 assignee 仅为业务关系，单独校验 ProjectAccess |
| ID 校验口径不一致 | 400/404 用例漂移 | 在 API 契约固定解析与存在性检查顺序 |
| Migration/Compose 不稳定 | 干净环境无法启动 | 从空数据卷执行完整启动回归 |
| 统计与任务状态不同步 | 页面显示错误 | 状态写入成功后刷新统计，并做已知数据集测试 |
| 10–25% 需求变化 | API/UI 返工 | 核心目标和 MVP 边界保持稳定，变更记录原因和影响 |
| API 契约和 README 漂移 | 验收无法复现 | 将状态码、错误结构、测试用户和命令作为发布核验项 |
